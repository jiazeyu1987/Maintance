# PRD — 完整程序包与逐目标受控升级

## Goal

在现有发布体系内，使完整包身份、目标升级计划、写入边界、运行身份和失败证据一致：同一包可针对不同受支持起点生成不同步骤，每个环境达到相同目标程序合同，保留自己的业务数据；不满足前提时明确停止。

本 PRD 交付本地代码、行为测试、真实隔离集成及文档，不把实际三服发布作为未经授权的动作。代码验收通过不等于现场旧基线已通过升级验收。

2026-09-26 用户范围纠正（CR-20260926-PROCESS）：交付目标为可复用的发布流程，不针对当前主程序代码版本发布。主程序主仓持续变化，不再追踪或合并其最新内容。固定任务应用切片只验证发布工作流接口；当前主仓合入、某次候选包构建、三服实时计划和实际部署均不属于本轮完成条件。AC-01～AC-12及完整流程回归保持不变。

## Scope

1. 收紧标准 `app-release` 的完整组件/制品合同和晋级入口，禁止组件缩窄及包外模板补齐。
2. 复用迁移计划器和既有目标数据预检，补齐历史状态阻断、包/目标/执行器/关键状态绑定与锁内复核。
3. 把常规部署只读预检移至目标运行配置或持久数据写入之前，停止隐式平台初始化/自动挂载准备。
4. 对实际运行组件核对不可变内容身份，生成持久的逐环境部署结果。
5. 持久记录执行阶段、可能写入、失败观测与恢复要求；连接既有工作流和写入 fence，防止未知状态被当作安全重试。
6. 保留三模式、三环境、同包测试晋级、原有测试证明和两入口工作流合同。

核心完整集合为 backend + frontend；保留显式产品范围 `intruoyi` 与 `full`（后者额外包含 Website），本包和所有目标必须同时交付/验证所有已纳入组件。标准 app-release 不再接受 backend/frontend/website-only 单组件包，禁止目标侧组件覆盖或缩窄。Website/OnlyOffice 的纳入情况固定在 manifest 并明确记录；未纳入本包的独立产品不能被错误宣称与全局 IMAGE_TAG 同版。MySQL、Redis、MinIO 等平台/持久服务按声明前提检查，不因程序完整交付而自动重建或清空。

## Non-Goals

- 不以持续变化的主程序主仓为本轮发布候选，不同步其业务改动或实施本次版本发布。
- 不另写一套发布控制台，不重设计正在进行的“两入口”任务或新增测试专用 UI。
- 不替换整个迁移工具链，不自动根据 schema 差异生成 SQL，不修正历史 SQL/迁移台账来放行。
- 不进行测试、正式、备份服务器的发布、重启、清锁、挂载、数据迁移、恢复或实时配置修复。
- 不实施 Kubernetes、零停机蓝绿、平台服务自动升级、灾备数据同步或完整恢复系统；没有这些能力时不作相应承诺。
- 不向包添加目标凭据、业务快照、目标执行计划；不修改已经冻结的包。

## User or System Scenarios

- BDD: 完整程序包发布 -> Given 构建范围包含完整 IntRuoyi 核心组件，When 构建并部署标准 app-release，Then 包具有全部必需输入且每个受管组件来自该包，部署参数不能缩窄其范围。
- BDD: 包缺少安装输入 -> Given 包缺少 Compose、所选展厅模板或声明必需的载荷，When 校验/准备部署，Then 在目标写入前失败并指出缺项，即使执行工作区存在同名文件也不补齐。
- BDD: 同包不同起点 -> Given 同一固定迁移链和三个通过真实前提检查的目标起点，When 使用同一计划器生成计划，Then 各自只执行尚未完成的合法步骤，绑定相同包身份和各自目标状态。
- BDD: 历史迁移异常 -> Given 目标存在 FAILED/RUNNING、成功记录摘要不符或依赖不满足，When 生成计划，Then 明确阻断且不自动重跑/改写异常记录。
- BDD: 预检失败无运行写入 -> Given 持久挂载、配置、控制表合同或数据预检不满足，When 请求部署，Then 原应用配置、容器、schema 和业务数据保持不变，输出具体阻断原因。
- BDD: 计划过期 -> Given 预检计划生成后目标关键状态发生改变，When 取锁后准备写入，Then 旧计划被拒绝，没有迁移或应用切换。
- BDD: 同标签异内容 -> Given 实际容器标签与目标相同但 imageId 不同，When 安装验收，Then 失败并报告期望与实际身份，不记录成功晋级。
- BDD: 迁移后切换失败 -> Given 已执行部分迁移或已开始应用切换，When 执行或验证异常，Then 保留阶段及真实观测证据、进入需要恢复/未知状态的保护合同，不声称已自动回退。
- BDD: 执行器中断 -> Given 某阶段可能已经写入但执行器停止，When 再次读取状态或请求部署，Then 使用持久阶段和锁证据识别未解决状态，不能仅根据过期心跳重新派发。
- BDD: 保留历史业务数据 -> Given 隔离数据库包含可追踪历史业务记录且挂载位置已确认，When 从受支持旧基线完整升级，Then 历史记录和存储位置保留，只应用包内声明迁移。

## Functional Requirements

### FR-01 完整、不可变的包合同

包保留 releaseTag、packageDigest、manifestDigest、来源提交及组件集合。核心 backend/frontend 必须齐全；Website/OnlyOffice 的纳入情况仅在构建时确定并记录。每个所选组件的制品和运行控制模板必须被 manifest 覆盖并校验。需要的宿主工具必须明确为包内载荷或有版本/身份检查的平台前提，不能依赖旧应用目录偶然存在。旧包缺少新合同字段应清楚拒绝并要求重新构建，禁止自行补写不可变包。

### FR-02 按目标生成确定性计划

同一个规划逻辑读取包内固定迁移、目标完整相关台账、真实 schema/数据前提和运行环境证据。相同合法输入产生相同动作和顺序；已成功且摘要一致的迁移跳过；历史摘要漂移、FAILED/RUNNING、未知状态、依赖缺失/环、必需真实前提不满足阻断。现有经校验的 metadata-only 等价摘要可以保留；不得添加任意摘要白名单。并行任务已验证的显式 supersession 合同只能按正式基线接入，不能借此隐藏未解释失败。

计划保存在包外，至少绑定包双摘要、releaseTag、目标环境/主机和数据库身份、执行器/计划器身份、采集时间、相关 schema/迁移/运行配置及持久挂载状态指纹、动作列表及阻断原因。指纹不记录秘密明文。计划通过仅允许进入执行门禁，不代表安装成功。

### FR-03 首次运行写入前门禁

顺序为包本地校验 → 目标只读预检与计划 → 取得既有持久部署锁 → 锁内重新核对关键状态 → 写入执行。目标只读阶段不得创建/修复挂载、目录、Compose、控制表、存储过程或业务数据；缺少既有平台/控制 schema 时指出正式准备前提。锁和操作记录是控制面写入，应明确区分于运行配置/业务数据写入，不能笼统声称完全零写入。

只允许计划中的迁移执行，沿用既有每步前写入 fence、迁移台账和目标数据 preflight。平台首次初始化独立于常规 app-release；当前任务不得用自动初始化让预检通过。

### FR-04 程序替换和数据边界

发布使用包内完整程序制品重建所选应用实例，环境秘密来自目标配置合同。持久数据库/附件/对象存储位置保持既有身份；禁止源库覆盖、MinIO 快照导入、自动创建空存储和全栈清空。程序替换不要求重新安装 MySQL/MinIO 或重置业务配置。历史数据保留证据应从真实隔离升级前后读取；不能仅以没有 DROP TABLE 文本作为证明。

### FR-05 运行身份和成功回执

镜像型受管组件核对包内 imageId 与实际容器 `.Image`，标签仅作辅助；展厅等静态载荷核对包内文件摘要和实际部署载荷身份。成功回执存放包外的持久 operation/部署证据目录，包含目标身份、包双摘要、期望/实际组件身份、schema/迁移结果、非秘密配置指纹、健康结果和成功时间。只有全部通过才能写 SUCCESS/APPLIED 及晋级历史；`.env` 或一个组件成功不能代表整体成功。

### FR-06 失败和中断证据

执行前持久记录原运行身份和目标身份，并在每个可能运行写入的阶段开始前记录阶段及 `writeAttempted` 类证据；阶段完成后记录结果。异常时保留已执行迁移、最后阶段、原始错误的脱敏摘要和实际运行态观测。观测失败明确标为 unknown/error，同时保留原始失败，不吞异常。

预检拒绝可证明无运行/业务写入；一旦可能发生迁移或切换而结果不能证明安全，既有操作/工作流必须进入需恢复状态或等价的持久阻断状态，后续部署不能越过。不能自动假设旧版本已恢复、按心跳过期清锁、盲重跑 SQL 或删除失败证据。恢复方法记录具体需要核实的阶段和状态；自动恢复/数据恢复不在本次新增范围。

### FR-07 现有调用方兼容

保留来源绑定、测试证明、正式授权、三环境参数和同包晋级模式；对不再允许的单组件输入返回稳定可定位错误，不静默改成 full。新增证据需要既有持久部署门禁或 workflow 的实际消费，不能仅创建脱离操作记录的文件。当前应用调用方已使用 intruoyi/full 且部署不覆盖组件，优先仅在维护仓修改；不得为了抽象“贯通”而无依据改写未完成两入口应用。出现具体必要的 API/参数变化时由主管协调并在集成结果上回归。

## Non-Functional Requirements

- Fail fast，不新增 fallback、降级、静默异常或默认成功；错误定位到缺失前提、具体迁移或组件。
- UTF-8 无 BOM 中文文件，日志和证据脱敏，不持久化密码/token/连接串。
- 包冻结后不可修改；计划、运行回执和失败证据不进入包摘要。
- 使用现有 PowerShell/Python/Java 技术栈和标准能力，避免另建通用发布框架。
- 各步骤证据可被独立测试者重放/核验。静态检查仅作补充，不能替代核心行为测试和真实隔离升级验证。

## Dependencies and Constraints

执行使用维护仓当前 int_main 的任务自有隔离 worktree。通过显式依赖任务复用已提交 P1 `772fc46` 的相关 15 个生产/测试路径，在主线 RED 后纳入并独立回归；不导入 d316da9 的 input-preparation 或未完成两入口 P2–P5 的应用/UI。并行任务工作区只读，其后续验收不构成本任务阻塞。现有源选择、包治理、目标数据 preflight、锁 schema 和应用工作流是复用边界，应用主线默认只读消费方。

本地已确认 Docker 29.2.1、MySQL 8.0.39 镜像、PowerShell 5.1/pwsh、Python、Node 可用；真实验证仍须独立容器/数据卷/端口，不使用正式数据副本，不影响本机共享业务资源。关键 SQL/SSH shell 必须验证实际生产函数和生成命令。缺少任务隔离资源时相应 AC 不得标通过。维护仓 legacy 调用方 `backend/src/main/java/com/intruoyi/maintenance/runtime/RuntimeControlOperationAction.java` 实际存在且被 Git 跟踪；测试应将其与 `E:/IntRuoyi/IntRuoyiBackend` 中实际应用调用方分别核对，不能把忽略规则导致的搜索遗漏写成文件不存在，也不创建假文件/副本。未修改 UI 时不要求创建 UI；若应用调用合同改动影响现有交互，则增加真实 Playwright 验证，不允许 API/SQL 代替登录后操作。

三服现场缺失前提、存储隔离修正、历史锁处理和具体升级支持证据需后续授权现场任务；本任务不得将它们标为已解决。缺 origin 影响推送/收尾，不影响本地实现授权。

## Acceptance Criteria

| ID | 可验收结果 | 最低验证证据 |
|---|---|---|
| AC-01 | 标准 app-release 拒绝 backend/frontend/website 单组件包；核心完整包通过；晋级不能改变构建时组件集合 | 真实包治理函数及入口参数行为测试，正反例 |
| AC-02 | 缺任何必需控制文件/所选组件载荷时，在目标运行写入前失败；工作区同名模板不能补齐 | 缺 Compose、展厅模板、镜像载荷反例，包不可变摘要核对 |
| AC-03 | 同包对三个合法旧基线生成不同、确定且依赖有序的待执行清单，目标合同相同 | 实际计划器三起点矩阵与 CLI 测试，包双摘要不变 |
| AC-04 | 成功历史摘要漂移、FAILED/RUNNING、未知状态、缺依赖或环被明确阻断；完整相关台账不被成功过滤隐藏 | 实际计划器和状态采集行为测试；合法等价摘要回归 |
| AC-05 | 计划具有包、目标、执行器、相关状态绑定；锁内任一关键状态变化拒绝旧计划 | 绑定字段/指纹测试及真实执行门禁调用顺序证据 |
| AC-06 | 挂载/配置/控制 schema/数据预检失败前无运行目录或挂载修改、控制文件覆盖、DDL、容器切换；缺失资源不自动初始化 | 实际生产函数/命令路径行为测试，隔离系统前后状态核对 |
| AC-07 | 真实隔离旧库升级保留既有业务行和数据挂载，执行步骤严格来自通过的计划，无源库/对象快照覆盖 | 真实 MySQL 升级前后记录和台账断言；实际部署数据边界回归 |
| AC-08 | 同 tag 不同 imageId 被拒绝；所有所选组件真实身份与包一致才通过，静态载荷身份也可核对 | 真实 Docker 身份反例及成功例、静态载荷摘要验证 |
| AC-09 | SUCCESS/APPLIED 和晋级历史仅在全组件身份、迁移、配置及健康验证通过后产生；持久回执有目标及包双摘要 | 真实成功路径及单项失败反例，证据读取测试 |
| AC-10 | 迁移/切换开始后故障保留阶段、已执行步骤、原/目标/实际状态；无法观测明确未知；异常不被吞，失败证据不清理 | 至少迁移异常、切换/验证异常两类故障；实际函数/隔离集成证据 |
| AC-11 | 中断或可能写入失败被现有工作流/持久门禁识别为需恢复；不得按过期心跳重派发；预检拒绝不伪造运行写入 | 持久阶段重读、锁/工作流实际行为测试，zeroWriteEvidence 断言 |
| AC-12 | 来源选择、tested v2、三环境及正式授权合同不退化，集成后兼容两入口任务；用户/运维文档写清完整包、前置准备和恢复边界 | 定向回归与独立审查；若影响既有 UI 则补真实 Playwright 证据 |

所有 AC 使用先 BDD/RED、后实现/GREEN/REGRESSION，结果记录于 execution-log 与独立 test-report。测试替身可用于单元测试的命令边界和故障注入，但不能替代 AC-07/08 所要求的真实隔离引擎或伪装为三服发布成功。
