# 验证报告

## 结论

6 个里程碑总体正确，建议保留。用户提出的核心调整是正确的：真实增量备份和全量+增量链恢复必须进入第一版，不能作为后续优化。

但需要把“第一版”拆成能力边界：

- M1-M3：底层备份和恢复能力。
- M4：按钮化和受控操作入口。
- M5-M6：针对几百 GB 实际数据、版本变化、换机和长期运行的最终放行条件。

## 必须调整的四点

1. M1 增加独立恢复控制平面。业务后端停止后，仍要能启动恢复、查询 operation、读取日志；不能依赖同一个被恢复目标后端。
2. M1 增加数据库备份技术实测选型。几百 GB 下，逻辑备份与物理备份必须按停写时间、吞吐、临时空间、恢复时间和可迁移性实测决定，不能默认逻辑 dump。
3. M4 保留“恢复演练”和“覆盖当前测试服”两条不同动作。可以有两个主按钮，但恢复按钮内部必须先选模式；未演练通过不能启用覆盖恢复。
4. M5 改成支持矩阵。第一版支持明确的 OS/CPU/Docker/MySQL/MinIO/Redis/程序版本组合；不在矩阵内必须阻断，不能承诺任意历史版本自动恢复。

## 范围边界

- 不需要把合成全量、跨任意版本自动迁移、任意秒级整系统恢复放入第一版。
- 必须把全量基线、真实数据库增量、对象增删改、整链恢复、校验、隔离演练、容量与故障阻断放入第一版。
- 本评审未执行真实备份、恢复、远程服务器访问或数据写入。
