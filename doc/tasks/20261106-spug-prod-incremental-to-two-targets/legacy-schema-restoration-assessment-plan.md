## 目标、里程碑和预期验证

1. 核对当前目录中全部 108 个备份点与现有 13 个代表组的实际映射，不把代表组通过冒充全部点通过；若实际数量不同，保留原统计与当前证据差异。
2. 找出五个仅有旧数据库设置的组缺少哪些正式数据库/程序兼容证据。以已保留的原件和现有 recovery_program / recovery_data 代码为准，区分可从受校验 SQL 正式推导的内容与无法推导的原始事实。
3. 给出最小可持续的合同重构范围、Given/When/Then 和验证路径，父审后才进入 RED -> GREEN -> REGRESSION。按 AGENTS.md 的重构要求采用 Subagent-Driven Development。

## 设计约束检查

- 是否引入 fallback/降级/吞异常：否。未知表结构、原件损坏和程序不兼容必须可见，不伪造旧备份的成功或完整性。
- 是否从根因和长期维护角度解决：是。正式支持明确的旧格式和恢复验证合同，不能把缺少源侧快照硬编码成通过。
- 是否存在临时补丁或绕过：否。评估阶段不修改归档、pin、运行配置、冻结实现或测试。

## BDD（评估与后续设计）

- Given 当前完整目录及分组报告，When 对每个备份点逐项关联，Then 每点有原来源、完整链、原程序、数据库证据类别和缺口，未映射及重复明确暴露。
- Given 旧归档仅存数据库设置，When 评估恢复校验合同，Then 区分原始 SQL 可证明的 schema/数据和当前证据无法证明的事实；不得用当前库或样本组替代其历史内容。
- Given 原始 pin 不符，When 设计支持方案，Then 保留失败，不通过重新计算清单或改历史修复。

## 经验门禁

- Trigger：全部历史点恢复验收仍缺旧格式数据库及程序兼容证据。
- Preflight check：现存公开报告和明确指向的私密原件；只读本机文件；当前安装/发布读取器冻结。
- Blocker：无原件、映射缺失、pin 不符、需真实 SQL/服务器操作或涉及原私密正文公开。
- Verification：逐点计数与证据定位、现有代码具体调用链、明确未验证项、可实施 BDD/TDD 方案。
- Forbidden action：不递归扫描 PRIVATE、不联网、不改产品/服务器/归档/数据库、不执行旧任务脚本，不把同组代表结果提升成所有点已通过。
- Evidence：archive-source-program-assessment-r3.json、archive-program-contract-evidence-r3.json、既有目录原件及后续专属评估文档。
