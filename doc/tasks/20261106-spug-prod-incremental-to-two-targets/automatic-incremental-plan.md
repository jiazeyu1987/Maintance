## 用户目标
用户要求点击 Spug 的“增量备份”按钮后，系统自行识别上一次成功全量及后续增量基线，执行真实增量备份，不再依赖 Codex 选点、临时脚本或人工 SSH。用户同时要求主动补齐相关遗漏。

## 目标与边界
- 将选链、前置检查、任务提交、进度、结果及失败恢复状态固化到正式产品代码。
- 以同一来源的完整成功链为依据选择最新有效链端点；不得依据目录名或仅按列表排序选择。
- 基线选择须与实际执行绑定，处理并发点击、过期页面、运行中任务、失败点和缺失日志。
- 检测全库恢复后的备份周期，明确显示需要建立新全量基线的原因和实际备份类型；不把全量伪称增量，不跳过丢失日志或静默换链。
- 检查 SQL 重复归档、程序镜像重复归档、流式读取和容量预估的正式可维护方案。只有恢复合同与旧包兼容验证通过后才改变新包格式。
- 当前原任务的两服恢复、失败原件与旧备份链保持独立验收；活动恢复期间不得替换其控制组件或输入。

## 设计约束检查
- 是否引入 fallback/降级/吞异常：否。需要新全量属于显式备份周期策略，页面与记录必须标注 FULL 及原因，不得将失败增量改记成功。
- 是否从根因和长期维护角度解决：是。以产品内的持久化选链与任务执行合同替代任务脚本参与。
- 是否存在临时补丁或绕过：否。不改变旧归档原字节，不删除失败历史，不绕过日志连续性、源身份、完整性或实际恢复验证。

## 初始 BDD 场景
- Given 同来源已有 F1；When 点击增量备份；Then 后台自动绑定 F1，成功产生 I1。
- Given 同来源已有 F1 -> I1；When 再次点击；Then 自动绑定 I1，产生 I2，恢复链为 F1 -> I1 -> I2。
- Given 最新尝试失败、另有其它来源或旧周期记录；When 点击；Then 不选失败点或其它来源，按已验证的当前成功链处理。
- Given 页面停留期间有另一任务提交或新点完成；When 点击；Then 服务端锁内重新确定计划，不并发派发同源备份或使用过期引用。
- Given 基线缺失、日志缺段、源库身份变化或全库恢复改变周期；When 点击；Then 返回明确的基线处理状态与原因，不伪装成成功增量。
- Given 任务已受理后浏览器关闭或请求超时；When 重开页面；Then 可查询同一后台任务，不重复提交。
