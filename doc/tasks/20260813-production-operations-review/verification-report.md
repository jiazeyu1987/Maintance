# 正式服日常运维模式评估报告

## 总体结论

当前系统已经具备较强的发布隔离、发布证据、版本回滚和完整备份恢复能力，但生产运维仍偏“有工具、靠人触发和复核”。正式服日常运维应从人工上服务器处理，转为以下四条持续闭环：

1. 变更可追溯：所有软件更新均由同一 `releaseTag` 从测试服逐级提升，不直接修改正式服务器。
2. 数据可恢复：自动备份必须有新鲜度告警、校验和、独立副本及定期恢复演练，不能只看备份文件是否存在。
3. 故障可发现：监控与告警必须运行在正式应用之外，避免系统自身故障时无法上报告警。
4. 数据可解释：运维分析与业务分析分层建设，避免用生产库临时 SQL 代替稳定指标体系。

## 当前能力与缺口

### 软件更新：流程较成熟

- 已有测试、正式、备用三环境和固定远端运行目录。
- 已有 `build-release -> publish-test -> mark-tested -> promote-prod -> promote-backup` 单一 `releaseTag` 发布闭环。
- 已要求从任务专用 clean release worktree 的已提交内容构建，并校验 operation、manifest、`.env IMAGE_TAG`、前后端实际镜像、后端 health 和前端 HTTP 200。
- 已有迁移策略门禁、正式发布 dry-run、回滚候选和操作证据校验。
- 风险：部署编排中 `onlyoffice/documentserver:latest` 未固定版本或镜像摘要，不能保证重建结果可重复；正式更新时不应隐式拉取漂移的 `latest`。

### 备份恢复：手工闭环已验证，自动化尚未闭环

- 当前配置目标为每日 `01:30` 备份、远端保留 30 天且至少保留 5 个备份点、本机临时副本保留 3 天、NAS 使用率上限 90%，周日 `02:00` 在备用服务器隔离演练。
- 备份范围包含 MySQL `ruoyi-vue-pro` 全量逻辑 dump、MinIO `yudao` 对象、DCC 范围清单、部署环境、镜像 tag、manifest 和 checksums。
- 2026-07-24 已有一次真实正式服备份和同一 `backupId` 的备用服务器隔离恢复演练；后端健康、前端 HTTP、登录和文件下载样本均通过，证明核心恢复链路曾经可用。
- 当前仅支持 full-dump baseline，没有 binlog/xtrabackup 增量链，因此不能宣称具备时间点恢复；在每日备份假设下，理论数据丢失窗口可能接近 24 小时，实际 RPO 必须由业务确认。
- MySQL 使用 `--single-transaction`，但 MySQL 与 MinIO 是分阶段采集；高并发写入期间的跨存储一致性仍需用业务一致性清单、短暂停写窗口或可验证水位解决。
- `notify.enabled=false`、`channel=pending`，备份失败目前没有已配置的外部通知通道。
- 计划任务注册脚本仅传 `-Mode`、配置、凭据路径和 `-NonInteractive`；正式 `backup-scheduled` 主入口同时强制要求 `-ProductionBackupConfirmText` 和显式 `-RepositoryEnvironment`。因此按当前源码注册的正式计划备份会 fail fast，不能把配置中的每日/每周时间当作自动备份已生效的证据。
- 仓库内未找到 `NextRunTime`、`LastTaskResult=0`、实际 `Task To Run` 或连续成功备份点证据，自动计划任务运行状态仍为未验证。

### 监控告警：具备运维工作台，缺少独立持续监控

- 主程序已有运行控制页面和接口，覆盖概览、业务健康、探针、容量、磁盘、备份点、告警、事件、巡检和责任人矩阵。
- 探针失败可生成告警并发送站内信；运行记录、告警、事件和责任人矩阵持久化为 `stateDir/runtime-ops/*.json`。
- 未发现这些运行探针和巡检的自动 `@Scheduled` 调度；当前入口表现为页面或 API 人工触发。
- 运行工作台与正式应用共用运行环境和站内信。若正式后端、主机或网络整体故障，工作台和站内信也可能同时不可用，因此不能作为唯一生产告警系统。
- 工程已包含 Actuator、Micrometer Prometheus、Druid、Spring Boot Admin 和 SkyWalking 依赖；但部署编排中未发现 Prometheus、Grafana、Alertmanager、集中日志或 SkyWalking 服务，SkyWalking 日志 appender 仍为注释状态。依赖存在不等于生产可观测性已启用。
- `application-dev.yaml` 暴露全部 Actuator 端点；正式环境实际 profile 未远端核实。正式运维应确认生产端点只对管理网开放，并按最小范围暴露。

### 数据分析：报表工具已存在，治理闭环不足

- 系统已有 JmReport、GoView、MES 报表、ERP/CRM/商城统计等能力，具备建设业务看板的技术基础。
- 当前未发现统一的指标口径目录、报表数据集责任人、数据质量告警、增量抽取水位或只读分析库证据。
- 备份库不能直接当分析库使用；备份目标是恢复，分析目标是稳定查询、口径一致和不影响生产负载。
- 正式分析不应由人员临时直连生产库执行重 SQL。应优先建设只读副本、增量数据集或汇总表，并对指标口径、刷新时间、租户边界和敏感字段脱敏负责。

## 推荐日常运维节奏

### 每日

- 由正式应用之外的监控节点持续检查前端、后端 health、关键登录/查询路径、容器状态、CPU、内存、磁盘、inode、数据库连接、Redis、MinIO、NAS 挂载和证书/域名到期状态。
- 每天确认最近备份点的新鲜度、manifest/checksum、MySQL dump、对象 inventory 和备份仓容量；失败必须自动通知责任人并形成事件。
- 查看新增应用错误、慢 SQL、失败定时任务、接口错误率和关键业务积压，只处理异常，不做无变更依据的例行重启。

### 每周

- 复盘告警、事件、慢 SQL、容量增长、备份耗时/大小和失败任务；把无动作价值的告警降噪，把漏报补成明确规则。
- 在备用服务器执行隔离恢复演练，随机抽取一个符合保留策略的有效备份点，并验证登录、关键查询和文件下载；禁止覆盖备用服务器正常 runtime。
- 检查依赖和镜像安全更新，但先在测试环境验证，不在正式服直接拉取或升级。

### 每月维护窗口

- 应用更新严格走同一 `releaseTag` 全链路；发布前确认最新可恢复备份点和回滚候选，发布后观察关键指标再提升备用服务器。
- 操作系统、Docker、数据库、Redis、OnlyOffice 和基础镜像补丁先在测试环境验证兼容性，再在批准窗口执行；生产镜像固定版本或 digest。
- 形成月度运维报告：可用性、发布成功率、故障与恢复时间、备份成功率、恢复演练、容量增长、慢 SQL、数据质量、权限变更和下月风险。

### 每季度

- 执行一次完整灾备演练，包括主机不可用、数据库恢复、对象恢复、配置/秘密恢复、备用服务器接管和回切步骤，并按实际耗时校准 RTO/RPO。
- 复核账号权限、密钥轮换、审计日志、备份保留、不可变/离线副本、容量预测和供应商/镜像版本生命周期。
- 用真实生产基线确定容量与性能阈值；没有流量和延迟目标前，不虚构 SLO 或扩容结论。

## 数据分析建议

### 运维数据

- 建立按时间趋势的可用性、响应时间、错误率、资源饱和度、磁盘增长、数据库慢查询、容器重启、备份耗时/大小和发布结果看板。
- 每个告警必须包含阈值依据、责任人、通知通道和处置 runbook；阈值应基于 2 至 4 周基线再确定。

### 业务数据

- 优先定义 MES 核心口径：计划与实际、在制品、工单及时完成、工序周期、一次合格率、返工/报废、设备停机和 DCC 审批积压；仅启用当前真实数据模型能够可靠支持的指标。
- 建设只读分析路径：生产库增量抽取到报表库或汇总表，按租户隔离，记录水位、刷新时间、数据质量和口径版本。
- 对关键业务关系建立每日只读质量规则，例如孤儿引用、状态机冲突、重复活动记录、缺失文件对象和异常审批积压；异常进入告警/事件，不允许脚本自动改生产数据。

## 实施优先级

1. P0：修复计划任务注册参数契约，配置外部通知，并以 `Enabled/NextRunTime/LastTaskResult/Task To Run` 和连续成功备份点证明自动备份真实运行。
2. P0：在备用服务器或独立运维节点部署外部探针和告警通道；正式应用内运行工作台作为操作台，不作为唯一监控源。
3. P0：由业务负责人确定 RTO、RPO、SLO、告警接收人与升级链路；未知目标保持 BLOCKED，不用默认值代替决策。
4. P1：固定 `OnlyOffice` 等第三方镜像版本，建设集中指标、日志、仪表盘和容量趋势。
5. P1：如果确认 RPO 小于每日备份窗口，实现并演练 MySQL binlog/PITR；禁止把全量 dump 静默包装成增量恢复能力。
6. P1：将高频管理分析迁移到只读报表数据集，建立指标目录和数据质量规则。
7. P2：增加独立故障域中的不可变或离线副本，并按季度完成全灾备接管/回切演练。

## 审查边界

- 本次未连接测试、正式或备用服务器，未读取秘密配置，未执行发布、备份、恢复、重启、数据库查询或远端写入。
- 计划任务实际状态、正式环境 active profile、现有告警接收人、真实业务 RTO/RPO/SLO、生产流量和成本均未获得运行证据，因此没有做成功或达标判断。
