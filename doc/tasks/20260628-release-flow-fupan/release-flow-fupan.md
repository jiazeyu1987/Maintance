# IntRuoyi 构建发布全链路复盘

## 1. 这次发布到底经历了什么

这次链路不是“一次成功”，而是从多个失败版本逐步收敛到最终成功的 `release-20260628-0015-head-full-v17`。中间暴露的问题覆盖了四个层面：

- 发布输入不干净或不一致
- SQL / migration 契约不满足发布门禁
- 发布脚本与业务仓产物契约漂移
- 服务器环境真实状态不满足发布前提

最终成功不是靠绕过，而是逐项把这些问题做成正式修复，并在测试服、正式服、备份服三段都完成真实运行态验证。

## 2. 从第一个失败版本到最后一个成功版本的关键演进

### 2.1 早期失败不是“服务器坏了”，而是发布输入和契约先坏了

最早几轮失败首先暴露的是发布门禁问题，而不是服务器问题：

- SQL 缺少 `release-migration` 元数据
- `dependsOn` 指向错误 migration id
- `system_menu.id` 使用变量而不是整数字面量，导致 migration policy gate 卡死

这说明一个长期规律：**发布失败时，先怀疑发布输入和契约，不要先怀疑环境**。因为连 manifest 前置门禁都过不了时，环境根本还没轮到。

### 2.2 中期失败暴露出“脚本契约”和“代码契约”漂移

中段的关键问题不是业务代码错，而是“业务仓已经改了，维护仓脚本还停在旧约定”：

- 后端已经改成 `spring-boot-maven-plugin + exec classifier`
- 但后端镜像仍复制 `yudao-server.jar`
- 维护仓发布脚本仍按旧 jar 名收集构建产物
- required SQL 排序和空集合处理在真实链路里有边界 bug

这类问题非常关键，因为本地单测可能是绿的，但真实发布链路仍会死。长期规律是：**发布脚本本身就是产品的一部分，不能当作“仓库外工具”随意维护**。

### 2.3 后期失败才进入正式环境真实问题

到了 v16 / v17，发布已经能稳定构建、稳定上测试服，问题开始收敛到正式服真实状态：

- DCC seed 在 prod/backup 环境缺少 tenant 1 授权变量
- DCC FVM SQL 基线写死 `active_total=60`，与正式服真实数据不符
- 正式服 `/mnt/nas` CIFS 挂载用户名错误，导致 Docker bind mount 失败

这一阶段的规律是：**一旦进入正式服问题，必须把“脚本问题 / SQL 契约问题 / 服务器状态问题”分开验证，不能混在一起猜**。

## 3. 后续怎么更稳地构建发布

### 3.1 构建发布前的固定顺序

后续每次发布前，建议严格按这个顺序：

1. 确认任务文档已创建，并写清楚目标 releaseTag、目标环境、验证方式。
2. 读取 `experience-index.md`，只打开命中文档。
3. 确认发布源头只在 `IntRuoyiMaintance`，业务代码只从 `IntRuoyi` 当前目标提交取输入。
4. 确认后端、前端、维护仓三方提交关系和 dirty 状态。
5. 先跑发布门禁和关键契约测试，再点页面构建。
6. 构建成功后先看 manifest，不以“界面看起来成功”作为唯一标准。
7. 发布测试服并验证运行态。
8. 只有测试服验证通过，才允许 `mark-tested`。
9. 只有 `mark-tested` 成功，才允许正式服。
10. 只有正式服验证通过，才允许备份服。

### 3.2 构建发布时必须固定的验证项

每次都必须显式验证：

- manifest 存在，且 `releaseTag`、后端 commit、前端 commit、`dirty=false` 正确
- 远端 `.env` 的 `IMAGE_TAG` 与本次 releaseTag 一致
- `docker compose ps` 中 backend/frontend 实际镜像 tag 正确
- 后端 `/actuator/health` 返回 `{"status":"UP"}`
- 前端入口返回 `200`
- operation 最终状态为 `SUCCESS`，不是只看健康检查

如果少了其中任意一项，就不能说“发布成功”。

### 3.3 服务器发布必须提前硬确认的参数

后续正式服 / 备份服发布前，必须预览并逐项确认：

- 目标主机 IP
- `RemoteAppDir`
- `RemoteReleaseRoot`
- `RemoteDataRoot`
- `RemoteDataDiskMount`
- `RemoteDataDiskDevice`
- `RemoteMinioContainer`
- `RequireTested`
- `ConfirmText=PROD`

特别是备份服，必须显式确认：

- `172.30.30.59`
- `/mnt/intruoyi-data`
- `/mnt/intruoyi-data/runtime-data`
- `/mnt/intruoyi-data/intruoyi-releases`
- `/dev/mapper/cl-home`
- `intruoyi-minio`

这次已经证明，**一旦这些参数靠默认值或历史值继承，就很容易把问题带到远端环境**。

## 4. 后续研发规范，不只是发布规范

这次复盘最重要的一点是：很多发布问题，其实在研发阶段就该被消灭，而不是等到发布时才发现。

### 4.1 SQL / migration 研发规范

- 新 SQL 必须带完整 `release-migration` 元数据。
- `dependsOn` 必须引用真实存在的 migration id，不允许靠记忆手写。
- 任何会进入发布扫描的 SQL，都要有契约测试或门禁验证。
- 涉及 `system_menu`、角色菜单、动态路由的 SQL，不允许再使用会触发发布门禁的变量式 id 写法。
- 环境相关 SQL 必须区分 test / prod / backup 的上下文，不允许默认共用一套隐式变量。

一句话：**SQL 不只是“能跑就行”，而是必须“能发布、能验证、能跨环境解释”**。

### 4.2 发布脚本研发规范

- 后端产物契约一旦变更，维护仓发布脚本必须同步改。
- 前端 build 命令、Docker build context、required SQL 排序、空集合处理，都必须有测试覆盖。
- 发布脚本中的环境分支必须显式，不允许靠“默认 prod”“默认旧 jar 名”“默认旧路径”工作。
- 维护仓脚本改动必须和真实页面链路一起验证，不能只跑单测就算完。

一句话：**发布脚本要按正式代码维护，不是按运维临时脚本维护**。

### 4.3 后端 / 前端研发规范

- 后端构建产物名称、Dockerfile、发布脚本三者必须保持同一契约。
- 前端和后端只要改了发布入口、资源路径、镜像结构，就必须回归发布链路。
- 不能把“本地能启动”当成“发布可用”；这次 `no main manifest attribute` 就是典型反例。

一句话：**影响发布链路的代码变更，必须把发布本身当成回归面的一部分**。

### 4.4 环境与运维研发规范

- `/mnt/nas`、数据盘、MinIO、容器挂载不是“环境背景”，而是发布前置条件。
- 服务器状态必须被当成显式证据管理，而不是靠经验猜它应该是好的。
- 修环境只能做最小正式修复，不能为了恢复发布去手工绕过发布链路。

一句话：**环境状态也是系统契约的一部分，必须可验证、可记录、可复查**。

## 5. 这次之后最该固化的执行规则

建议后续每次发布都默认执行下面这套“最小闭环”：

- 先建任务目录，再开始改代码或发版
- 先读经验索引，再做高风险动作
- 先过门禁和契约测试，再点页面构建
- 构建后先看 manifest，再看 operation
- 测试服先行，验证通过后再 `mark-tested`
- 正式服发布必须预览参数并确认 `PROD`
- 备份服必须显式确认数据盘与 MinIO 参数
- 每一步失败都先记录真实根因，再修复，再重走真实链路
- 不允许用 mock、手工改状态、手工 docker compose 代替发布链路成功

## 6. 对后续任务最有价值的三个结论

### 结论一：发布问题优先按“契约层”排查

后续遇到发布问题时，优先顺序应该是：

- 发布门禁 / manifest / migration 契约
- 发布脚本与业务仓产物契约
- 远端环境参数与挂载状态
- 最后才是单纯业务逻辑

这样能大幅减少盲查。

### 结论二：测试服不是形式流程，而是正式服的唯一前置筛选器

这次正式服最终能成功，是因为测试服已经先把：

- 迁移门禁问题
- jar 契约问题
- 脚本空集合问题
- 基本 SQL 链路问题

都提前筛掉了。后续不要再把测试服发布当成“走个形式”。

### 结论三：研发阶段就要写“可发布代码”，不是只写“可运行代码”

这次很多问题本质上都不是业务逻辑 bug，而是：

- 不可发布
- 不可迁移
- 不可跨环境
- 不可追溯

所以后续研发要默认面向“可发布性”写代码和脚本。

## 7. 后续可直接复用的简版清单

后续任何一次完整发布，先问自己这 10 个问题：

1. 任务文档建了吗？
2. 命中经验文档读了吗？
3. 三仓提交和 dirty 状态确认了吗？
4. migration / SQL 契约测试跑了吗？
5. 发布脚本和业务产物契约同步了吗？
6. manifest 校验项准备好了吗？
7. 测试服验证项列出来了吗？
8. 正式服预览参数逐项确认了吗？
9. 备份服数据盘 / MinIO 参数确认了吗？
10. 每一步失败是否有真实日志和真实证据，而不是猜测？

如果这 10 个问题有任何一个答不上来，就不应该直接开始正式发布。
