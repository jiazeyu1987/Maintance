## 4. 执行前的放行检查

真正执行时创建新的发布任务目录，记录目标 SHA、发布范围、三服授权、维护窗口、数据影响和恢复方式。按 `server-access.md`，正式和审查服需要显式确认 `PROD`；这是将来执行发布时的生产门禁，本次写方案不触发该操作。

逐项通过后，在该发布任务 `execution-log.md` 写入 `GREEN: experience-preflight -> PASS`；有失败则写明确 `BLOCKER` 并停止。

1. **唯一执行器和权威状态。** 沿用已确认的源机停止结论，执行前核实期间没有其他发布者接管、没有重复本机实例。232 条任务、25 个历史包只是上次验收基线，不能硬写回；检查实时 active、failed、interrupted、恢复待验收及维护未知状态。未决任务先按原记录核对，不能清空历史解除阻塞。状态备份使用 SQLite backup 接口，不能运行中只复制主数据库遗漏 WAL。
2. **准确目标。** 白名单读取三服登记配置，核对 host、容器 ID/名称、业务与验收 URL、数据库、数据盘、挂载、MinIO/Redis 和发布目录。三服旧容器名称不统一，不猜测标准名称。SSH 使用安装目录受限 ACL 的同一密钥及已知主机文件，`-F NUL`、BatchMode、IdentitiesOnly、StrictHostKeyChecking；不打印私钥、不关主机指纹校验、不猜密码、不自动改跳板。
3. **工具和本地资源。** 验证 Python、JDK、Maven、Node、pnpm、Docker、SSH/SCP、Playwright 和浏览器实际可运行；lockfile、基础镜像 ID、pnpm store 同文件系统硬链接条件通过。核对配置的 `localBuildSpaceBytes`；同盘预算相加。缺工具、镜像、缓存或网络时真实报错，不临时换运行时或跳过检查。
4. **NAS 和远端资源。** 使用仓库外私密凭据核对准确 NAS 目录权限、容量和原包上传后回读摘要。现有检查按钮会创建唯一的本地/NAS 临时文件验证读写、改名、删除；远端诊断本身不部署、不改库、不登记基线。远端按真实文件系统核对 Docker 导入余量、运行余量、恢复点与隔离副本容量，不能只看根盘总量。不得自动清理别人产物或对 `/mnt/nas` 删除、清空、卸载、改 fstab。
5. **迁移和目标起点。** 核对真实 `SHOW TABLES` / `DESCRIBE` / `SHOW CREATE TABLE`、迁移完整台账、未知/失败/运行中项、摘要及依赖闭包。显式 `release-sources.json` 分类完整，已执行 SQL 不修改或删除；新规则用新迁移。依赖不能仅“ID 存在”而目标语义不满足。目标结构或登记指纹变化就停止重新评估，不改 ledger、补成功记录或放宽预检。
6. **前置演练和验证。** 快速的迁移策略、manifest、菜单身份、脚本合同及必要行为测试先于 Maven/前端构建。按适用门禁在一次性同镜像 MySQL 完成结构 APPLY 演练；非结构迁移对真实目标做绑定迁移 ID 的只读 SELECT/CTE 预检。它不能替代第 7 节的正式完整数据隔离升级。临时资源必须精确清理并记录；缺条件直接停止。
7. **真实登录及业务范围。** 登录工具和各环境凭据仅从仓库外读取。本任务按用户基线使用 `测试租户 / aoteman`；先核实每个目标存在且权限满足，不因旧文档账号不同擅自切账号。Playwright 先填写真实租户登录表单，确认选中目标租户，再进入真实页面；接口只能辅助最终校验。登录或必要基线数据缺失时停止，不重置密码、补权限、改业务数据或 mock 成功。
8. **一致性和恢复资源。** 核对完整 writer 清单、停写/排空方式及数据库事务归零证据，覆盖任务、worker、MQ、外部接口和直接写入者；不能只拦 HTTP。数据库及 Redis/MinIO 的恢复范围、独占挂载、owner、保留策略、容量、恢复工具和私密访问必须经过实际核实；共享数据服务不能直接按独占实例停机或覆盖。

上述门禁如果暴露代码缺陷，先回所属仓库按 Given/When/Then、RED → GREEN → REGRESSION 修复并提交，再冻结新目标。若涉及重构，另按仓库规定执行；不在发布 worktree 塞未提交补丁继续发。

## 6. 一次构建，三服消费同一个不可变包

构建器会在 `buildWorktreeRoot/<releaseTag>` 创建本次新的 detached worktree，检出冻结完整 SHA；禁止跨任务复用旧 worktree，状态、日志、凭据和缓存留在源码树外。维护执行目录同样使用本次冻结代码。需要运行本地前后端时按正式端口登记，不抢主工作区端口。

构建执行本版本发布器固定的 Maven、pnpm frozen-lockfile、Vite 和镜像构建流程，不另外拼装 JAR/dist。当前后端打包命令包含 `-DskipTests`，所以“打包成功”不能代替前面独立完成的必要测试。

封包记录唯一 releaseTag、应用/维护 SHA、实际执行脚本摘要、工具版本、基础镜像 ID、迁移及预检/结构合同、release-info、前后端镜像 ID、各文件校验和、manifest SHA-256、release.tar SHA-256。导出前从前端镜像读回版本文件，导出及 NAS 回读再核摘要；私密文件与数据库/MinIO 全量数据不进轻量程序包。

从测试到审查全程冻结这份原包，**不重建、不改 SQL、不换镜像、不改 manifest**。若需要任何修改，必须形成新提交、新 releaseTag，重新测试和正式起点演练；不得拼接多轮成功结果。

## 7. 正式完整数据隔离演练与真正升级

正式演练使用当前正式环境的真实完整副本，并保持数据库、Redis、MinIO、网络和验收入口独立；绝不把正式备份导入正在服务的测试/审查业务库。副本禁止连接真实外部系统或执行真实发送、同步、定时写入。writer 隔离、存储 fence 和一致性证据不完整就不捕获或升级。

执行前检查演练网络不覆盖公司/VPN 网段及本机来源 IP，核对实际回程路由和从执行器到验收端口的可达性。端口探针仅证明可达，网关 502 不能当作应用健康或真实登录成功。缺少必要规则时独立审查精确来源及端口，不临时扩大防火墙权限。

正式发布前重新核对当前版本、镜像、结构、迁移台账与该演练绑定起点；业务数据可以继续变化，因此迁移的数据前置检查仍须用最新数据重新执行，并在停写、旧后端停止、事务归零后再次检查。起点不符或数据检查失败，停止，不能借用旧演练。

首次远端写入前确认该正式实现的任务互斥、远端操作记录/锁和归属检查生效；记录原任务与回执。不能因本机只有一个 Python 进程就认定不会有其他电脑并发发布，也不能混用其他发布器的锁与台账冒充已持有当前锁。

三服升级前按当前执行器要求，建立绑定**原部署任务、原包摘要、旧版本、结构、完整台账和完整数据**的恢复点；核验数据库及登记的 Redis/MinIO 数据范围和摘要。不能只保留旧镜像当作数据库回滚能力。正式/审查升级后保持维护，直到技术和业务验收都通过才开放。

业务验收只读取既有真实数据及此次变更涉及的关键页面，核对菜单、权限、版本说明和控制台/网络错误。没有前端入口或必要数据则如实阻塞；本方案不授权创建、编辑、删除、审批或第三方写入。如未来必须写入验收，应先明确范围，只能通过真实前端在测试租户创建有任务标识且可清理的数据。禁止修改芋道源码租户、受保护展厅配置/媒体域或 live 审核矩阵。

## 8. 每服怎样才算发布成功

每服、每次任务都保存同一 releaseTag 下的如下证据；缺一项不宣布该服完成，更不宣布三服完成。

| 检查 | 通过标准 |
|---|---|
| 操作终态 | 对应部署任务真实成功，无未决失败、迁移运行中或恢复待验收；Spug 原始状态是 `succeeded`。统一验收结论记为 operation=SUCCESS，同时保留原始状态；若底层还有独立 operation，另核它的真实成功终态，不手工改状态 |
| 原包及 manifest | releaseTag、完整源 SHA、packageSha256、manifestSha256、文件摘要、迁移/合同身份均匹配；三服消费同一包 |
| 远端运行配置 | 已明确的权威 `.env IMAGE_TAG` 与本包一致，且配置真实用于目标实例；禁止仅创建一个不生效的 `.env` 文件满足检查 |
| 实际镜像 | backend/frontend 实际 image ID 或 config digest 匹配 manifest；对应 tag 同样正确。不能只比较 `Config.Image` 字符串，因为当前可能直接使用 `sha256:…` 启动 |
| 后端 | 当前实际后端健康检查返回 UP；无 Docker HEALTHCHECK 的容器不能仅看 `running` 当健康 |
| 前端 | 当前登记的真实入口 HTTP 200，镜像内、发布版本文件、页面编译版本一致；Playwright 真实登录进入登录后页面，核租户身份、版本与变更说明，记录控制台/网络异常 |

还须核迁移台账完整且没有未执行项，正式/审查业务验收通过并真正开放。最终交付一张三服对照表，列出主机/URL、releaseTag、源 SHA、包双摘要、任务 ID、演练 ID、恢复点 ID、`.env`、镜像 tag/ID、health、HTTP、Playwright、业务验收及维护状态，并附脱敏证据路径和每阶段耗时。只展示“命令退出 0”不算完整证据。

## 9. 失败时我会怎么处理

| 失败阶段 | 处理方式 |
|---|---|
| 更新、预检或构建失败 | 停止发布；保留失败原因和不完整尝试，不宣称包可用。修复正式代码后重新冻结构建；不改摘要、跳测试或假造成功 |
| 测试或正式演练失败 | 正式/审查服不推广；保留 SQL、台账、容器与原任务证据。需要改程序或迁移则新包重新走链路，不修改失败包 |
| SSH 超时、执行器退出、返回丢失 | 不立即重发。先通过“中断核对”确认原本机子进程、远端原回执和实际影响；远端仍运行则等待，已完成则续验收，未知则保持阻塞 |
| 正式/审查部分迁移失败，或开放前验收失败 | 保持维护。使用原任务的恢复面板核对恢复点，明确恢复原因，经授权按原恢复日志恢复旧程序及完整数据，保留故障库/目录/容器。恢复后仍需真实登录、业务验收和显式开放，不能直接重跑部分成功 SQL |
| 正式已开放后发现问题 | **不直接恢复升级前数据库**，以免丢失开放后新数据。停止后续推广，保全当前数据与现场，先评估兼容回退/前向修复和数据影响，另行确定正式处置；不能把开放前恢复入口当万能回滚 |
| 正式成功、审查失败 | 正式结果保留，但整次三服任务仍未完成。先收束审查原失败/恢复责任；符合当前入口条件时通过“仅补发备用服”使用正式当前已验收的同一原包，关联原失败任务，不重发正式服 |

历史包中只有部分原件随资源包携带，其他只是历史记录。回退前必须验证所需原包/镜像/恢复点实际可读及摘要匹配，不能根据版本下拉框有该版本就承诺可恢复。恢复、故障处理不自动清理失败证据。
