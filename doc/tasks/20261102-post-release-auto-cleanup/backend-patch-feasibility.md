# 后端补丁包可行性核查

## Current Status
completed（本轮可行性核查完成，尚未实现后端补丁能力）

## 目标、里程碑与预期验证
用户询问是否可以做后端补丁包。本轮形成可审阅的范围与接入方案，核对当前执行器是否支持及现有依赖，不修改生产代码、不构建补丁、不连接三服、不发布。里程碑：定位后端构建与版本合同、确认前端补丁的限制、提出后端专用补丁的适用条件和恢复边界。沿用现有任务链，不改变主任务尚未收尾/扩展事项。

## 经验门禁
- Trigger：新增发布方式的可行性分析。
- Preflight check：依据当前运行代码核构建、启动、版本、GxP、恢复及清理合同，区分建议与已实现能力。
- Blocker：未明确数据库/配置/API兼容性、启动迁移或恢复边界时，不将具体改动认定为可后端单发。
- Verification：只读追踪真实入口；方案列清前提、三服顺序和可回退范围。
- Forbidden action：不得直接复用前端补丁包冒充后端补丁，不运行构建/发布/服务器动作，不输出秘密，不增加发布前全量备份或演练。
- Evidence：本文件与 execution-log.md。

## 设计约束检查
- 是否引入 fallback/降级/吞异常：否。
- 是否从根因和长期维护角度解决：是，提出独立后端补丁合同而不是手工换 jar。
- 是否存在临时补丁或绕过：否。

## 结论
可以建设后端专用补丁，但现用执行器没有 backend-patch 动作，维护仓对应目录也未发现 backendPatch/backend-patch 实现。现有前端补丁清单只接受 frontend 镜像，且绑定 backendImageId；不能把后端镜像放进前端补丁包或绕过清单手工替换。

## 建议首版范围

- 仅用于兼容当前前端、当前数据库及当前运行配置的后端代码修复。不含数据库结构/数据迁移、菜单权限/初始化数据变更、启动所需新配置、外部运行依赖切换或不兼容 API/序列化数据变更；这些仍走完整发布。
- 固定已提交源码，在独立发布 worktree 编译整个后端 JAR 及镜像，记录源 commit、基础完整版本、原/新后端镜像、适用前端和数据库结构/迁移台账身份、配置身份及摘要。包只有新后端镜像和清单等控制文件，不做 class 热替换。
- 一次构建同一包逐服：测试部署/真实页面验收 -> 正式部署/验收 -> 备份部署/验收。复用任务持久化、互斥、上传校验、真实起点复核和逐目标状态；不增加用户已取消的演练或发布前全量备份。
- 受控停写/排空请求及任务后替换后端并保留原容器，前端资源及数据库服务保持原版本；后端短暂不可用期间页面 API 会受影响。新后端先按现有维护协议验证、再开放，不承诺零停机。
- 启动后核真实后端补丁身份/镜像、health、writer controls、GxP 保存和运行态均关闭、前端兼容性及真实登录/变更场景；复核 schema/ledger 未发生补丁范围外变动。没有数据库/配置兼容性证据不得称为安全补丁。
- 失败可显式恢复原后端程序；这只能恢复程序，不撤销新代码已提交的业务数据或外部动作。因此持久化格式、业务写入语义和任务副作用也必须评审兼容性，不能只凭 SQL 文件未变化认定可回退。
- 版本体系需独立 backendPatchTag；前端补丁当前强绑定后端镜像，新增后端补丁后必须同步扩展组合基线识别、恢复绑定、状态/UI、完整发布接续和清理保护。后续完整包目标提交必须包含仍在用的前后端补丁提交，避免覆盖已上线修复。
