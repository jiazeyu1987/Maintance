# 单 JAR 发布方式说明

## Current Status
completed（可行性核查完成，未实施 JAR 发布通道）

## 目标与验证
用户询问是否能仅替换一个 JAR。沿用当前任务链，只读核实既有 JAR 路径、启动命令和镜像身份约束，区分技术可行与现有 Spug 能力；不改生产代码、不连接服务器、不执行发布。预计核对启动合同后给出可持续的轻量方案和恢复边界。

## 经验门禁
- Trigger：改变后端制品投递方式的机制说明。
- Preflight check：读取发布备份恢复规则及构建制品合同；核实制品路径，不能把镜像 ID 当作挂载 JAR 的真实身份。
- Blocker：未纳入 JAR 摘要、版本/恢复绑定和 GxP/兼容性验证时不得称为现成发布能力。
- Verification：交叉核对构建 Dockerfile 与运行配置继承逻辑，无远端动作。
- Forbidden action：不直接覆盖运行容器、不改凭据、不运行构建/重启/发布，不新增演练或全量数据备份。
- Evidence：本文件和 execution-log.md。

## 设计约束检查
- 是否引入 fallback/降级/吞异常：否。
- 是否从根因和长期维护角度解决：是，制品身份、版本目录和恢复路径一并设计。
- 是否存在临时补丁或绕过：否。

## 核查结论
可以仅投递一个完整可执行 JAR，不必每次传整个 Docker 镜像。此前将后端镜像描述成后端补丁的必需制品过于绝对。当前构建把 `yudao-server-exec.jar` 作为 `app.jar` 复制进镜像，工作目录 `/yudao-server`，通过 `java ${JAVA_OPTS} -jar app.jar ${ARGS} ${INTRUOYI_EXTRA_ARGS}` 启动。已有部署与验收合同以镜像为主体，尚无正式 JAR-only 工作流。

建议正式方案为固定 Java 运行镜像 + 按版本保存的不可变 JAR + 小型清单。每次只传新 JAR 和清单，核对 SHA-256、源提交、基础版本/当前前端、schema/ledger、运行配置及 Java 兼容性；保持现有参数和秘密来源。排空后停止旧后端、保留原容器，创建只读挂载该版本 JAR 的新后端并启动，校验真实 JAR 身份/运行版本、健康、GxP 关闭、真实页面与变更功能。同一 JAR 测试/正式/备份逐服验收，不重新加入演练或全量数据备份。

不能继续仅凭镜像 tag 判断后端版本：镜像相同但挂载 JAR 不同，实际程序已不同；状态、清单、验收、恢复及清理需纳入 JAR SHA、版本目录和实际启动挂载。恢复显式切回原容器/原版本 JAR，程序恢复不撤销业务数据。已固定的版本文件不得原位覆盖，也不能在旧进程还运行时变更它正在使用的 JAR。当前镜像内置模式转挂载模式需要实现与验证，不应直接在现用容器中 docker cp 覆盖后宣称版本发布完成。

此方式仍需重新编译完整可执行后端 JAR，包含依赖，不是只替换一个功能的 class；Java 基础环境、数据库/配置/API或数据格式不兼容时超出这条轻量通道。三服无需收到前端包或整套数据库副本。后端切换仍有短暂不可用。

代码证据：活跃 `intruoyi_build.py:368` JAR 复制、`:373` 启动命令；`intruoyi_runtime_agent.py:626` 克隆原配置、`:674` 保留原容器再创建新容器；`build_artifact_guard.py:99` 核对镜像内真实 JAR SHA。只读核查完成，无程序变更、构建或远端动作。
