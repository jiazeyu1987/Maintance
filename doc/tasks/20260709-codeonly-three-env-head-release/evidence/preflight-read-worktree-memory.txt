# Worktree 记忆规则

## 触发条件

- worktree 创建、切换、排障、合并、清理、删除。
- 多仓并行开发、前后端成对分支、发布隔离 worktree。
- 涉及本地端口、运行态归属、E2E 目标串线或提交隔离的任务。

## 强制门禁

- IntRuoyi 根目录只作为协调目录；融合、验证和提交判断以前后端仓库为准。
- 后端仓库固定为 `ruoyi-vue-pro`，前端仓库固定为 `yudao-ui-admin-vue3`。
- 并行开发默认一任务一独立 worktree，前后端成对创建同名分支。
- 涉及登录、E2E 或发布时，还要读取对应登录、服务器和发布经验文档。
- 新建 worktree 前必须明确前后端分支、路径、端口和依赖目标。
- worktree 路径必须符合仓库标准脚本可识别模式；本项目本机标准路径优先使用 `D:\ProjectPackage\Int\IntRuoyiWorktrees\<worktree-name>\...`，不要放在脚本未收录的自定义目录名下。
- 启动或 E2E 前必须做运行态归属校验，确认前端、后端、数据库、Redis 和文件服务指向本任务目标。
- 在把某个端口当作真实验收入口前，必须先证明它属于当前 worktree；`8081/48081` 默认视为主工作区 `int_main`，除非已有证据证明当前任务显式接管了它们。
- 真实 E2E 或登录前置开始前，前后端都必须启动成功；前端可访问但后端 `/actuator/health` 不通时，直接判定运行态未就绪，不得继续把前端页面当作有效验收环境。
- 合并后必须在合并结果上验证相关功能；验证未通过不得清理 worktree。
- 清理前必须预览并确认只处理本任务 worktree、运行时和临时产物。
- 同文件混入其他任务 hunk 时，不得整文件暂存；必须人工拆分或在干净 worktree 重放补丁。

## 常见失败模式

- 端口、日志、数据库连接和 E2E 目标比代码冲突更容易串线。
- 新前端 worktree 可能缺少 `node_modules`，类型检查前需先确认依赖。
- 新前端 worktree 若缺少 `node_modules`，官方 `login-preflight.mjs` 会在启动浏览器前直接报 `Cannot find module 'playwright'`；这属于依赖前置未满足，不是业务登录失败。
- `8081/48081` 是主工作区默认端口，并行 worktree 不应默认复用。
- worktree 若放在 `D:\ProjectPackage\Int\IntRuoyi-worktrees\...` 这类非标准目录下，端口台账/标准脚本可能无法识别，导致 FE/BE 端口解析失败或误判。
- 前端 worktree 已启动且归属正确，不代表后端也已就绪；若 FE 端口正常、BE 端口未监听或 `/actuator/health` 失败，应优先抓后端启动日志，而不是继续怀疑前端代理或业务链路。
- 根目录 Git 状态不能代表前后端仓库已经融合完成。
- 路径级 `git add <file>` 会把同文件其他任务 hunk 一起带入提交。

## 验证命令

- 后端 `/actuator/health` 来自目标 worktree。
- 前端访问目标端口，首个业务接口命中目标后端。
- E2E 证据记录真实 `baseUrl`、后端地址、租户账号和关键接口命中结果。
- 自动化入口：`node scripts/preflight/worktree-preflight.mjs --root <repo> --branch <branch> --backend-path <dir> --frontend-path <dir>`

## 阅读时机

凡任务涉及 worktree 创建、切换、排障、合并、清理、分支同步或多仓协同时，先阅读本文件，再执行命令。

## 固定仓库边界

- IntRuoyi 根目录只作为协调目录，不作为融合结果判断项。
- 后端 Git 仓库固定为 `ruoyi-vue-pro`。
- 前端 Git 仓库固定为 `yudao-ui-admin-vue3`。
- 融合、验证和提交判断以前后端两个 Git 仓库为准。

## 分支与 worktree 规则

- 本项目是混合 Git 工作区；凡要求新建或使用新分支，必须在每个相关 Git 仓库创建同名分支。
- Codex 并行开发默认一任务一独立 worktree 工作区。
- 前后端成对创建同名分支，根目录只用于协调与最终集成。
- 不要把根目录 Git 状态当作前后端融合完成的依据。

## 运行时隔离规则

- 多 worktree 并行开发时，问题高发点不是代码冲突，而是前端端口、后端端口、日志、数据库连接和 E2E 目标串线。
- 每个 worktree 必须绑定独立的前后端端口对；不要默认复用 `8081/48081`。
- `8081/48081` 只保留给主工作区，或明确废弃；并行 worktree 一律使用显式分配端口。
- 推荐为每个 worktree 固定一组可追溯端口，例如 `paichan_v2 -> 8084/48084`、`scheduler_workbench -> 8085/48085`，避免临时口头约定。
- 前端和后端端口必须成对记录，禁止只改一侧端口后继续沿用旧代理配置。
- 除前后端端口外，还要同时记录当前 worktree 实际依赖的数据库、Redis、文件服务和本地代理端口；不要默认它们天然跟随前后端一起隔离。

## 端口台账规则

- 仓库内应长期维护一份可共享的 worktree 端口台账，至少记录：`worktree 名称 -> FE 端口 -> BE 端口 -> DB/Redis 目标 -> 负责人/任务编号`。
- 新建 worktree 前先登记端口，避免“先抢到哪个端口就用哪个”的临时行为。
- 旧 worktree 停用或删除后，要同步回收台账，避免后续误判某组端口仍在使用。

### 推荐台账字段

- `worktree 名称`
- `任务编号`
- `前端仓库路径`
- `后端仓库路径`
- `前端分支`
- `后端分支`
- `FE 端口`
- `BE 端口`
- `前端 baseUrl`
- `后端 actuator 地址`
- `DB 地址`
- `Redis 地址`
- `测试租户/样本占用说明`
- `负责人`
- `状态`：`规划中 / 运行中 / 已停用 / 已清理`
- `最后更新时间`

### 推荐台账格式

- 推荐使用统一表格，至少保持以下列顺序，便于脚本后续读取：

| worktree | task | fe_port | be_port | base_url | actuator | db | redis | sample_usage | owner | status | updated_at |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| paichan_v2 | 20260609-scheduling-development-plan-edhr-impact | 8084 | 48084 | http://127.0.0.1:8084 | http://127.0.0.1:48084/actuator/health | 127.0.0.2:23306/ruoyi-vue-pro | 127.0.0.2:26379 | 测试租户 881MO090880 | codex | 运行中 | 2026-06-10 09:30 |

## worktree 运行时目录规则

- 每个 worktree 根目录下应保留独立 `.runtime/` 目录，至少记录：
- `frontend.pid`
- `backend.pid`
- `frontend.log`
- `backend.log`
- `runtime.env`
- `runtime.env` 必须记录当前 worktree 的前端地址、后端地址、代理目标、数据库目标和必要启动参数。
- `runtime.env` 还应记录当前运行实例的 `worktree 名称`、`分支名`、`启动时间`、`提交号` 和 `任务编号`，保证截图、日志和问题单能追到具体运行态。
- 需要排障时，优先查看当前 worktree 的 `.runtime/`，不要先猜测某个全局端口属于谁。

## 启动与停止规则

- worktree 运行时必须通过统一脚本启动、停止和查询状态，不要长期依赖手工散落命令。
- 推荐提供统一脚本，例如 `runtime-up`、`runtime-down`、`runtime-status`，由脚本根据当前 worktree 自动写入 `.runtime/`。
- 启动脚本必须在启动前检查目标端口是否已被占用，并输出占用进程与归属路径。
- 启动脚本必须在启动后再做一次自检，确认前端实际监听在预期端口、后端健康检查返回正常、前端代理实际命中预期后端。
- 若前端启动成功但后端未监听预期端口，不得只记录“后端没起来”；必须继续抓取当前 worktree 后端标准脚本输出或启动日志，把失败根因落到可复现证据上。
- 停止脚本只能停止当前 worktree 在 `.runtime/` 中登记的进程，不得顺手清理其他 worktree 的运行时。
- 若端口被未知进程占用，先定位占用进程路径和命令行；在未确认归属前，不得直接 kill。

## 前端验证环境规则

- 新建或恢复 `yudao-ui-admin-vue3` worktree 后，运行前端类型检查前先确认 `node_modules` 存在；缺失时先在当前前端 worktree 执行 `pnpm install`，不要把缺依赖误判为代码错误。
- `yudao-ui-admin-vue3` 执行 `pnpm ts:check` / `vue-tsc` 时默认设置 `NODE_OPTIONS=--max-old-space-size=8192`；默认 4GB 堆内存容易 OOM。
- PowerShell 示例：`$env:NODE_OPTIONS='--max-old-space-size=8192'; pnpm ts:check`。
- 如果 8GB 堆内存下仍 OOM，按资源前置条件不足 fail fast 记录，不要静默跳过类型检查，也不要把 OOM 归因于业务代码。
- 发布专用 frontend worktree 也必须按同一依赖规则处理；新建后若缺少 `node_modules`，先执行 `pnpm install --frozen-lockfile`，锁文件或依赖解析变化必须阻断出包，不得用主工作区依赖目录替代。

## 最小启动清单

- 新建或恢复一个 worktree 运行态前，至少完成以下检查：
- 确认当前所在目录就是目标 worktree，而不是主工作区或其他并行 worktree。
- 确认当前分支名与任务名一致，前后端 worktree 成对存在。
- 确认 worktree 路径本身能被标准端口脚本识别；若路径模式不符合脚本约定，先迁移到标准目录再继续。
- 确认本次使用的 FE/BE 端口已在台账登记，且未被其他 worktree 占用。
- 确认前端依赖已就绪；若后续要跑 `login-preflight.mjs`、Playwright 或业务 E2E，先验证当前前端 worktree 已安装 `node_modules` 且 `playwright` 可解析。
- 确认 `.runtime/runtime.env` 已更新为本次 worktree 的真实运行参数。
- 确认前端代理地址、后端数据库地址、Redis 地址与本次验证目标一致。
- 确认后端实例已真正监听预期端口，且 `/actuator/health` 可达；仅有前端页面 200 不算运行态 ready。
- 若缺少其中任一项，不要直接启动或验证，先补齐再继续。

### 启动前标准问答

- 我现在所在目录是不是目标 worktree。
- 我的 worktree 路径是不是标准脚本能识别的目录模式。
- 我即将启动的 FE/BE 端口是不是台账中分配给这个 worktree 的端口。
- 我当前前端 worktree 是否已经具备 `node_modules` 和 Playwright 依赖，能跑官方登录前置。
- 我现在的前端代理是不是明确指向本 worktree 后端。
- 我的后端实例是否已经能通过 `/actuator/health`，而不是只看到前端页面能打开。
- 我要写入的数据库和租户是不是本次允许操作的目标。
- 我有没有记录这次会占用的真实样本编码或批次前缀。

## 运行态归属校验规则

- 任何需要登录、写数据、跑 E2E、截图、录屏或联调的动作前，先做一次“运行态归属校验”。
- 归属校验至少包括：
- 当前浏览器访问的 URL 是否为本 worktree 分配端口。
- 当前前端页面是否携带可识别的 runtime 标识。
- 当前后端 `/actuator/health` 是否来自本 worktree 预期实例。
- 当前前端请求是否实际命中本 worktree 对应的后端地址。
- 若归属校验有一项不成立，先停止当前验证，修正运行态，再继续业务操作。
- 若发现 `8081/48081` 实际仍归属于 `int_main`，必须立即切回当前 worktree 分配端口，不得继续复用主工作区运行态做证据。

### 验证前检查清单

- 浏览器地址栏是否为本 worktree 的 FE 端口。
- 页面是否显示本 worktree 的 runtime 标识。
- 后端健康检查是否返回本次 worktree 对应实例。
- 打开的第一个业务接口请求是否命中本次 worktree 对应后端。
- 当前租户、账号、样本编码是否与本次验证计划一致。
- 若涉及写数据，是否已经确认旧测试记录已清理，或明确本次会新写哪些记录。

## 前端识别规则

- 开发环境页面应尽量显示当前 runtime 标识，例如 `worktree 名称 + FE 端口 + BE 端口`。
- 真实页面验证、截图和录屏时，优先保留该标识，避免后续无法判断页面实际连接的是哪套运行时。
- 发现页面访问正常但接口行为异常时，先核对当前页面是否连到了本 worktree 的后端，而不是直接怀疑业务代码。

## E2E 与真实验证规则

- E2E 脚本不得写死共享默认端口；必须显式从环境变量或当前 worktree 的 `.runtime/runtime.env` 读取 `baseUrl` 和 `api base`。
- 真实验证前，先确认当前前端实际代理到目标后端，再开始登录、写数据或排障。
- 本地浏览器实际请求地址要以 DevTools/Playwright `request.url()` 为准；如果页面访问 `127.0.0.1` 但接口实际打到 `localhost`，可能因 IPv4/IPv6 或旧 Vite 进程导致连接拒绝。先重启当前 worktree 前端并显式设置 `VITE_BASE_URL` / `VITE_PROXY_TARGET`，不要把网络地址串线误判成权限或业务接口失败。
- 若同一测试租户样本已被前一次 E2E 消耗，优先清理本次验证留下的测试记录，或补一组新的最小真实样本，再继续验证。
- 不能把“页面能打开”当成验证通过；必须确认接口请求命中了当前 worktree 对应的后端。
- E2E 启动阶段必须 fail fast：若 `baseUrl`、后端接口地址、租户、账号、目标工单或目标批次前缀不符合当前 worktree 约定，立即退出，不要边跑边猜。
- E2E 证据中必须记录本次实际访问的 `baseUrl`、后端地址、批次号前缀和关键接口命中结果，避免后续把别的 worktree 结果误当成本次结果。

## 测试数据占用规则

- 多 worktree 并行期间，测试租户中的“可写样本”视为共享资源，不能默认认为自己独占。
- 需要消耗一次性样本时，先记录样本编码、租户、用途和当前 worktree，避免多个 worktree 抢同一条真实数据。
- 若验证会改变样本状态，例如生成排产工单、提交报工、推进审批、写入批次号，验证结束后要么回滚本次测试记录，要么更新台账说明该样本已被占用。
- 对一次性样本的清理、软删除或回滚，只能在明确知道来源与影响范围后执行，不得为继续测试而盲删。

## 配置与默认值规则

- 多 worktree 并行期间，禁止依赖“默认 localhost 入口”“默认代理配置”“默认数据库端口”来推断当前运行态。
- 前端 `.env`、后端启动参数、E2E 环境变量都必须显式写出当前 worktree 的端口和依赖目标。
- 同一个仓库若保留主工作区默认端口，也要明确写清：哪些脚本只允许主工作区使用，哪些脚本必须由 worktree 显式覆盖。

## 合并与清理规则

- worktree 合并后，必须在合并结果上验证相关功能正确性。
- 验证未通过，不得视为完成，也不得继续清理 worktree。
- 清理 worktree 前，必须确认本任务相关提交已经完成，且没有混入用户改动、其他 Agent 改动或临时输出。
- 合并前，必须停止当前 worktree 自己启动的前后端进程，或至少确认 `.runtime/` 中的运行态不会继续误导后续任务。
- 删除 worktree 前，必须清理或归档 `.runtime/` 信息，避免端口台账和日志指向已不存在的工作区。

### int_main 融合前主工作区冲突门禁

- 凡任务分支或 worktree 需要融合进 `int_main` 时，必须优先在对应主工作区完成融合；禁止为了绕过主工作区脏改而新建临时 merge worktree 作为最终融合路径，除非用户明确授权。
- 融合前必须检查前后端主工作区 `int_main` 的 `git status`、本次任务分支相对 `int_main` 的变更文件列表，以及二者是否存在文件级或 hunk 级重叠。
- 若主工作区脏改与本次任务分支存在重叠、冲突或无法判断归属，必须暂停融合；先按改动归属拆分处理：能确认属于已完成任务且通过必要验证的改动，分别在对应仓库单独提交；来源不明、半成品、验证不足或与当前融合冲突的改动，不得强行提交，必须记录为阻塞并请用户确认。
- 若主工作区存在未提交改动但与本次任务分支无重叠、无冲突，允许继续融合；融合前必须记录无关脏改清单，融合时不得暂存、提交、覆盖或格式化这些无关改动。
- 禁止用“隔离 merge worktree 验证通过”替代主工作区 `int_main` 的最终融合与验证。最终验收必须基于主工作区 `int_main`，在任务分支合入后启动并验证。
- 若无法安全判断主工作区脏改是否与本次融合冲突，当前任务融合状态必须标记为阻塞；不得继续合并、不得删除原任务 worktree、不得声称已完成融合。
### 合并前检查清单

- 前后端两个仓库是否都在目标 worktree 分支并完成提交。
- 合并目标是否明确为对应仓库的 `int_main`，而不是根目录 Git。
- 真实验证证据是否明确记录了本次 worktree 的 FE/BE 地址和关键接口命中结果。
- 如果 E2E 脚本最初写在任务 worktree 中，合并后必须复跑并确认脚本参数已切换到主工作区路径和主线端口；不得让脚本继续引用已删除 worktree 的目录、截图路径或服务端口。
- `.runtime/` 中登记的进程是否已停止或已明确交接。
- 端口台账中的状态是否已更新，避免后续继续把该 worktree 视为运行中。

### 混合工作区提交隔离门禁

- 收口前除 `git status` 外，还要查看 `git diff --stat`，必要时检查共享文件 hunk，重点关注 `docs/request-command-log.md`、任务文档、`package.json`、公共 E2E gate 和共享脚本。
- 路径级 `git add <file>` 只适用于该文件 diff 全部属于当前任务；同一 hunk 混入跨任务内容时，不能靠整文件暂存实现隔离。
- 正式处理路径是干净 per-task worktree/branch 重放当前任务补丁并复验，或人工 hunk 拆分后复验；无法做到时记录提交隔离阻塞，不合并、不清理、不按提交策略标完成。
- 嵌套仓库改动必须在 owning 仓库内提交：前端 `yudao-ui-admin-vue3` 的源码和测试只提交到前端仓；根仓只提交任务文档、共享日志等根仓文件。提交前分别执行根仓和子仓的路径限定 `git status` / `git diff --cached --name-only`，不要用根仓状态推断子仓是否已干净。
- 共享日志、任务索引、公共脚本这类长文件提交前必须查看实际 diff；若同一文件中已有无关历史脏改或编码污染，先恢复/拆分到只剩本任务 hunk，再提交。不能因为“只追加了本次记录”就直接整文件 `git add`。
- 发布/出包属于提交隔离场景；主工作区存在非本任务脏改时，不得直接构建发布包。必须创建前后端成对的干净发布 worktree/branch，重放当前任务补丁，在隔离 worktree 内完成测试、类型检查和发布脚本前置验证。
- 发布 worktree 如果只用于构建发布包且不启动本地服务，可以不登记 FE/BE 运行端口；但必须在任务文档中记录 worktree 路径、前后端分支、相关 commit、构建命令和验证命令。若后续启动服务、联调或 E2E，则立即按端口台账登记。

## 禁止事项

- 不得用 worktree 状态替代真实功能验证。
- 不得在未确认目标仓库和分支的情况下执行删除、移动或合并操作。
- 不得为了绕过冲突、缺失依赖或验证失败而引入 fallback、临时补丁或静默跳过。
- 不得在只删除了 Git worktree 注册后就认定目录已清理完成；Windows 上残留的 `node_modules`、运行时文件或被占用文件必须通过固定根路径校验后再处理。
- 指定了完整 worktree 路径时，不需要再向用户索要 `worktree-name`；以用户给定路径作为唯一权威目标，分支名可按任务命名规则自动派生，但所有创建、运行、融合和删除动作都必须回到该绝对路径校验。
- `git worktree remove` 成功清掉注册项后，物理目录仍可能因为运行进程、深层 `node_modules` 或 Windows 长路径残留；必须同时验证 `git worktree list` 无目标注册、目标目录不存在、前后端子目录不存在，三者都成立才算清理完成。
- 清理残留目录前先停止当前任务 worktree 自己启动的前端、后端、构建器等运行进程；进程匹配必须限定命令行包含目标 worktree 路径，并排除当前执行壳，避免误杀正在执行清理命令的 PowerShell。

## 2026-07-06 发布 worktree 长路径门禁

### 触发场景

- code-only 或完整发布需要同时创建维护仓、后端仓、前端仓临时发布 worktree。
- 任务 ID 较长，且临时根路径直接使用完整任务名，例如 `D:\ProjectPackage\Int\IntRuoyiWorktrees\20260706-codeonly-three-env-current-head-release`。

### 经验规则

- 发布 worktree 根目录必须使用短路径命名，优先使用 `D:\ProjectPackage\Int\IntRuoyiWorktrees\r<日期><短标识>`，仓库子目录也使用短名，例如 `m`、`b`、`f`。
- 创建三仓 release worktree 前，先计算维护仓、后端仓、前端仓目标路径长度；任一路径可能接近 Windows 长路径风险时，直接改用短根路径，不要先尝试长任务名路径。
- 若维护仓检出因 `Filename too long` 失败，必须立即冻结失败证据、检查已部分创建的后端/前端 worktree、清理失败根目录并执行 `git worktree prune` 后再重建。

### 禁止做法

- 禁止在长路径 checkout 失败后继续使用已部分创建的后端/前端 worktree 发布。
- 禁止把路径过长失败当作 Git 临时故障反复重试。
- 禁止为了绕过失败复用主工作区或旧 release worktree。

### 验证方式

- 重建后记录三仓 worktree 路径、commit、branch/detached 状态和 `dirty=false`。
- 确认失败长路径不再出现在 `git worktree list --porcelain`，且短路径 worktree 在标准边界 `D:\ProjectPackage\Int\IntRuoyiWorktrees` 内。

## 2026-07-06 电子签名证据链融合复验经验

### 触发场景

- 功能在独立 worktree 完成后融合回前后端 `int_main`。
- 真实 E2E 脚本最初依赖任务 worktree 的前后端路径、端口、截图目录或临时服务。
- 清理时 Git worktree 注册已删除，但 Windows 文件目录仍残留。

### 经验规则

- 融合后必须在主工作区 `int_main` 上重新执行真实 E2E，且证据中记录主线 `baseUrl`、后端地址、租户、账号、关键记录 ID 和 hash；任务 worktree 中的通过结果只能作为开发阶段证据。
- E2E 脚本应从环境变量读取前端入口、后端地址、图片 ID、版本号、文件 ID 和期望 hash；脚本默认值若指向任务 worktree，合并后必须改为主工作区可复用默认值或在命令中显式覆盖。
- 删除 worktree 前先停止运行态、确认 `git worktree list --porcelain` 中已无目标注册，再检查目标目录是否仍存在；目录存在时先确认绝对路径位于 `D:\ProjectPackage\Int\IntRuoyiWorktrees\<task>` 边界内，再清理残留。
- Windows 上 `Remove-Item -Recurse` 清理深层 `node_modules` 失败时，不要扩大删除范围；先做固定路径边界校验，再使用 UTF-8 aware runtime 的递归删除能力处理该任务目录。

### 验证方式

- 主线复验记录主仓前后端 HEAD、`baseUrl`、`backendUrl`、测试租户账号、证据记录主键和 hash。
- 清理完成后同时验证：目标 worktree 注册为空、目标目录不存在、主工作区相关仓库状态未被清理动作污染。
