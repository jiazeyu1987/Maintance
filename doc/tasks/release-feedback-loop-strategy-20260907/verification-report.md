# 发布失败反馈闭环长期方案

## 核心结论

长期方案不是让失败安装包反复修改后继续用，而是建立“反馈前移 + 环境镜像 + 缓存构建 + 不可变制品晋级”四层体系。

已经进入发布并暴露源码或制品缺陷的 releaseTag 仍应判废，修复后生成新 releaseTag。节省时间主要来自两处：大部分错误在完整构建前 1 至数分钟内暴露；确需生成新包时复用依赖和镜像层缓存，只重建受影响部分。

## 目标流程

```text
代码提交
  -> 快速静态预检
  -> 目标服务器只读预检
  -> 缓存化构建安装包
  -> 临时同构环境安装演练
  -> 发布同一包到测试服
  -> 真实验收并绑定 package digest
  -> 原包晋级正式服
```

## 四层长期机制

### 1. 打包前快速门禁

在 Maven、前端构建和 Docker 打包前运行，优先控制在短反馈阶段：

- Git worktree、commit、dirty、依赖 lockfile 和工具版本。
- SQL migration metadata、依赖链、MySQL 标识符/临时表/collation/幂等性静态合同。
- manifest schema、环境变量声明、端口、镜像 tag/digest 和秘密扫描。
- 按变更文件计算受影响模块，未通过时不创建 releaseTag、不启动完整构建。

### 2. 目标服务器只读预检前移

服务器错误往往不是“打包错误”，而是包与目标当前状态不兼容。应在完整构建前只读采集：

- 当前 schema、migration ledger、菜单/权限占用和关键配置基线。
- 磁盘空间、Docker/Compose 版本、端口占用、挂载、依赖镜像和外部服务可达性。
- 目标环境必要秘密是否存在，只报告字段存在性，不读取或记录秘密值。
- 根据候选 commit 的迁移清单生成 target-bound `preflight-plan`；存在 blocker 时不打包。

对本项目而言，这一层优先级最高。历史多次失败是 required SQL 与测试服真实 schema/ledger 不一致，静态编译成功无法发现。

### 3. 可缓存、可增量的正式构建

- Maven 本地仓库、pnpm store、前端依赖按 lockfile 哈希缓存。
- Docker 使用 BuildKit layer cache，并固定基础镜像 digest；不再每次 `--no-cache` 全量构建。
- 后端、前端、Website 和可选组件按变更范围构建，但最终仍组合成一个有完整 manifest 的安装包。
- 缓存只加速构建，不能进入 manifest 作为未验证旧产物；输出文件仍逐项计算 SHA-256。

### 4. 用真实安装包做同构演练

- 建立可销毁的 release qualification 环境，其 Docker Compose、MySQL/Redis 版本和服务器目录契约与测试/正式服一致。
- 不从源码直接启动，而是安装刚生成的同一个归档包。
- 执行迁移 dry-run、容器启动、health、前端 HTTP、关键 smoke 和回滚演练。
- 演练通过才将包原子写入 NAS `READY` 候选区；测试服和正式服不得重新构建。

## 失败分类与处理

| 失败位置 | 是否打包 | 是否重打 | 正确处理 |
| --- | --- | --- | --- |
| 静态/依赖预检 | 否 | 否 | 修复后重跑秒级预检 |
| 目标只读预检 | 否 | 否 | 修复环境契约或迁移设计后再预检 |
| 正式构建 | 未完成 | 是，新 tag | 使用缓存只重建受影响层 |
| 同构安装演练 | 已完成但未入库 | 是，新 tag | 把故障补成更早门禁 |
| 测试服发布 | 已入库 | 是，新 tag | 冻结失败证据，修复根因并重建 |
| 正式服发布 | 同一合格包 | 不重新构建 | 先回滚并查环境漂移；制品有缺陷则新 tag |

## 当前项目最值得先做的五项

1. 增加一个统一 `release-preflight` 动作，全部通过前禁用“构建安装包”。
2. 把测试服 target-state 和 `preflight-plan` 从 publish-test 阶段移到 build-release 之前。
3. 去掉应用镜像构建的无条件 `--no-cache`，改用受控 BuildKit 缓存并验证最终哈希。
4. 建立临时同构环境，自动安装真实发布包并跑迁移、health 和 smoke。
5. 每次服务器新故障必须增加一个能更早复现它的合同测试或 preflight 检查，形成持续收敛的错误知识库。

## 衡量方式

先记录基线，不虚构目标值：

- 失败首次被发现的阶段，以及发现耗时。
- 每个成功 releaseTag 发生了几次完整 build-release。
- preflight 拦截的错误数和服务器阶段新增错误数。
- Maven、pnpm、Docker 各层缓存命中与耗时。
- 测试服和正式服 package digest 是否完全一致。

现有实测记录显示，一次成功 build-release 约 14.01 分钟、publish-test 约 4.84 分钟；一次依赖缺失导致约 8.20 分钟额外开销。把依赖和 target-state 门禁前移，比单纯让打包脚本跑得更快收益更稳定。

## Boundary

- 本任务只形成方案，没有修改发布代码、运行构建、连接服务器或执行发布。
- 实施时应按 BDD + 严格 TDD 分阶段交付，先做统一 preflight，再做缓存和同构演练。
