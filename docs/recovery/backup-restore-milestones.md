# 测试服务器备份与恢复演练：六个里程碑实施文档

日期：2026-09-18

审查修订：2026-09-19

文档状态：方案已审查；运行态未验证

适用对象：ChatGPT 网页介绍、产品评审、后端/前端实现、测试验收、运维演练

目标环境：测试服务器

版本范围：第一版必须覆盖实际全量、真实增量和全量加增量链恢复

## 1. 给 ChatGPT 网页的背景说明

当前需要为一台测试服务器建设可操作、可验证的备份与恢复演练能力。用户希望在页面上通过两个主要入口完成：

1. 点击“立即备份”，在测试服务器侧执行备份。
2. 点击“选择备份包恢复”，从服务器备份仓库选择恢复点，执行恢复演练，必要时再经过明确确认替换当前测试环境。

数据量预计为几百 GB，因此第一版不能只验证“生成了一个备份文件”，也不能把真实增量和全量加增量整链恢复推迟到后续优化。备份和恢复必须在服务器侧完成，不能让浏览器或用户电脑中转几百 GB 数据。

本项目还必须考虑以下变化：测试服务器升级、降级、换同架构硬件、跨 CPU 架构、磁盘或 NAS 更换、目录/IP/域名变化、数据库和对象存储版本变化、密钥不可用、原服务器完全不可用，以及恢复之后形成新的备份历史分支。

## 3. 总体决策

六个里程碑的拆分是正确的，保留六个，不再增加一个“按钮开发”或“增量优化”之外的附加里程碑。但需要把第一版分成两个放行层次：

| 放行层次 | 包含范围 | 可以宣称的能力 |
| --- | --- | --- |
| V1 功能闭环 | M1-M4 | 有经过约束的全量、真实增量、整链恢复能力和页面操作入口，可进行受控演练 |
| V1 实际放行 | M1-M6 | 在实际几百 GB 数据规模下，通过性能、版本、换机、故障、保留和持续运行验收 |

没有 M5-M6 的证据，不能把 M1-M4 的功能成功描述成“已经支持几百 GB 生产级恢复”或“任意升级、降级、换硬件都可以恢复”。

## 4. 不可删减的横向硬门禁

这些不是第七个里程碑，而是 M1-M6 每一阶段都必须遵守的合同。

### 4.1 独立恢复控制平面

备份恢复任务、任务状态、日志、锁和恢复候选查询必须由独立的控制平面承载。被恢复的业务后端可能需要停止、可能已经损坏或尚未启动，因此恢复控制平面不能完全依赖目标业务后端。控制平面、候选目录和审计记录应位于不同于目标业务数据的故障域；如果控制平面本身不可用，必须能够从不可变工具 artifact、备份仓库的签名 manifest 和仓库保留元数据在其它机器重新启动并重建候选目录。

至少应能在业务后端停止时完成：创建恢复任务、查询 `operationId`、读取阶段进度、查看阻断原因和导出恢复证据。

### 4.2 恢复点是封存的一致性状态

数据库和对象存储必须属于同一个已封存的业务状态，不能只记录一个时间戳或列出一份文件名就宣称两者一致。恢复点需要定义：

- 数据库一致性位置：例如 GTID、binlog 起止位置、LSN 或选定物理备份位置。
- 对象状态：新增、修改、删除、版本和内容校验。
- 写入协调：所有 writer 是否已停止、排空或被 fence。
- 恢复点唯一标识：`restorePointId`、`backupId`、`baseBackupId` 和 `parentBackupId`。

第一版只承诺恢复到已封存的完整业务备份点，不承诺数据库与文件能够自动恢复到任意一秒。

### 4.3 RPO 与 RTO 的统一口径

RPO 以数据库和对象共同拥有的恢复点计算，不以数据库最后一条 binlog、对象最后修改时间或某一个服务的时间戳单独计算。业务允许丢失的数据必须明确为“从哪个 `restorePointId` 起算到故障时刻”，并分别记录数据库和对象两边的最大差距。

页面和验收报告必须同时区分：

| 指标 | 含义 |
| --- | --- |
| 目标 RPO | 业务 owner 批准的最大可接受数据丢失窗口 |
| 当前保护点年龄 | 当前时间减去最新 `COMPLETE` 且链完整的数据库/对象共同恢复点；只表示已封存，不等于已演练 |
| 已证明恢复点年龄 | 当前时间减去最近一次真实恢复成功且证明仍未 `STALE` 的共同恢复点 |

只有当前保护点年龄不超过目标 RPO、链和签名检查通过、且演练证明未超过 M1 规定的新鲜度，才能把 RPO 状态显示为通过；否则必须显示超期、未验证或阻断。

RTO 至少拆成两个指标，起止点必须在 M1 固定：

| 指标 | 计时范围 |
| --- | --- |
| 演练 RTO | 服务端接受恢复任务开始，到隔离目标恢复、业务关键校验和演练报告生成结束 |
| 覆盖 RTO | 获得授权并开始停写/fence 现环境，到目标环境切换、健康检查、关键业务校验和重新开放写入结束 |

备份仓库读取、镜像/工具准备、数据库重建、对象恢复、索引重建、校验和人工审批是否计入，必须在 M1 写入同一份 RTO 合同。未知的 RPO/RTO 不能用“后续再测”带过，必须作为 blocker。

### 4.4 备份集必须有完整状态和清单

“备份包”在几百 GB 场景下指一个由 manifest 统一描述的不可变备份集，不要求也不建议把数据库、对象和增量日志压成单一巨大文件。备份集可以由分块、数据库备份、binlog/物理增量段、对象增量、删除 tombstone、镜像/工具引用和 manifest 组成；只有所有必需成员校验完成后，逻辑上的 `backupId` 才能封存为完整备份集。

不可变 manifest 建议至少包含以下字段；detached 签名封套位于 manifest 外部，签名对象是 `manifestDigest`，避免自引用：

```text
backupId
manifestVersion
backupType: FULL | INCREMENTAL
generationId
baseBackupId
parentBackupId
restorePointId
sourceEnvironment
sourceFingerprint
programImageDigests
toolImageDigests
schemaFingerprint
dbBackupMethod
dbLogStart / dbLogEnd / GTID 或物理增量位置
objectInventoryDigest
payloadInventoryDigest / payloadReferences
chainDigest
itemCount / byteCount
checksums
manifestDigest
signingKeyVersion
encryptionKeyReference / payloadEncryptionKeyVersion
createdAt / completedAt
```

外部 detached 签名封套至少包含 `manifestDigest`、签名算法、签名值、签名 key 标识和签名时间；它不能反向修改 manifest 内容。

可变状态不得写回并重签原 manifest，而应保存在独立候选目录和证明记录中：

```text
backupStatus: PLANNED | RUNNING | VERIFYING | COMPLETE | FAILED | INVALID | EXPIRED
rehearsalStatus: NOT_RUN | RUNNING | PASSED | FAILED | STALE
compatibilityStatus: UNKNOWN | PASSED | BLOCKED | STALE
targetFingerprint / evaluatedAt / candidateExpiresAt
retentionClass / retainUntil / legalHold
rehearsalEvidenceRef / compatibilityEvidenceRef
```

备份集中不能写入数据库密码、MinIO 密钥、SSH 私钥等明文秘密；`encryptionKeyReference` 只引用独立密钥保管系统中的密钥版本。加密 key 的可恢复生命周期不得短于其所保护备份集的保留期。校验和用于发现损坏，manifest 签名用于发现未授权篡改，两者不能相互替代。

建议使用以下状态：

```text
PLANNED -> RUNNING -> VERIFYING -> COMPLETE
                              \-> FAILED
COMPLETE -> INVALID | EXPIRED
```

`COMPLETE` 只表示备份集已封存并通过完整性校验，不表示已经通过实际恢复演练。`rehearsalStatus` 和 `compatibilityStatus` 必须按 `(backupId, chainDigest, targetFingerprint)` 分别记录，不能把在某一目标上的一次 PASS 当成所有目标通用。

这里要区分两类候选，避免循环依赖：

- “演练候选”：`backupStatus=COMPLETE`、manifest/checksum/签名通过、依赖链完整、源 fingerprint 和恢复位置完整；此时 `rehearsalStatus` 可以是 `NOT_RUN`，允许发起隔离演练。
- “受控恢复候选（覆盖候选）”：演练候选已经 `rehearsalStatus=PASSED`，且演练报告绑定相同的 `backupId`、`restorePointId`、`chainDigest`、`manifestDigest`、源 fingerprint、目标 fingerprint、程序镜像 digest 和工具版本；当前 manifest 签名仍受信任，目标兼容、权限和二次确认全部通过，并根据目标模式具备已验证保护点或空白目标证明。

一次 `PASSED` 不能永久授权未来覆盖。链内容、源环境、目标环境、镜像/工具、密钥版本、保留状态或演练报告过期后，必须变为 `STALE` 并重新演练。

### 4.5 不兼容时必须阻断

不允许自动忽略版本差异、吞掉异常、悄悄改变数据库备份方式、把增量改成全量、把演练改成覆盖恢复，或把失败结果包装成默认成功。缺少前置条件时必须返回明确 blocker 和证据。

### 4.6 恢复演练与覆盖当前测试服必须分开

页面可以只有两个主要入口，但后端必须有清晰的三个语义动作：

- `backup-now`：执行备份。
- `restore-rehearsal`：恢复到隔离目标，仅验证可恢复性。
- `restore-data`：在演练和兼容检查通过后执行受控恢复；覆盖现有环境时必须先创建保护点，重建空白/已毁目标时必须先证明目标为空且归属正确，两种模式都要经过二次确认。

未完成演练的备份集不得直接启用受控恢复。

### 4.7 当前实现与目标合同的差异

现有运行控制台的静态实现曾要求恢复候选已经 `rehearsalStatus=PASSED`。这只覆盖“已演练后受控恢复”，无法让操作人首次选择 `NOT_RUN` 但完整、已校验的备份集进行隔离演练。实现 M4 时必须拆分服务端候选查询或增加明确的 `candidateType`：

- `rehearsal-candidate`：允许 `COMPLETE + NOT_RUN`，只能进入隔离演练。
- `controlled-restore-candidate`：必须绑定目标 fingerprint 的有效 `PASSED` 演练报告，只能进入受控恢复。

在该接口和状态机差异修复并通过测试前，M4 不能放行。不能通过把所有候选永久标成 `PASSED` 或让前端绕过服务端候选检查来解决。

### 4.8 隔离演练必须隔离外部副作用

隔离恢复不只是换一个数据库目录。隔离槽位必须使用独立数据库、独立对象空间和独立 Redis namespace；Quartz/定时任务、MQ consumer、worker、Webhook、邮件、短信、外部 API 和其它会产生写入或通知的集成必须默认禁用，或只连接到专用的隔离端点。外联网络应采用 deny-by-default 的 allowlist，不能把真实生产或共享业务系统当作演练依赖。隔离槽位包含真实备份数据时，访问控制、加密、日志脱敏和到期清理不得弱于源环境，也不能开放为公共测试数据源。

Redis、队列和缓存必须在 M1 分类：可重建缓存可以清空，队列消息必须排空、隔离或采用明确的丢弃策略，不得在演练启动后重复消费造成外部副作用；如果其中包含不可替代业务状态，必须纳入正式备份和恢复校验。无法证明隔离副作用时，M2/M4 均不通过。

### 4.9 覆盖恢复必须避免半恢复环境

默认不得在当前对外提供服务的数据目录中原地覆盖恢复。应先恢复到新版本化目录、隔离槽位或可独立验证的快照目标，完成数据库、对象、配置和健康检查后再执行受控切换，并保留旧目标为只读回退证据；只有经过实测证明原地恢复具备事务性回滚和服务隔离能力时，才允许例外。健康检查失败不能自动把目标判定为空或触发 `REBUILD_EMPTY`。

备份仓库必须使用与源系统不同的凭据和权限边界：源系统只能追加/写入，不能删除或修改已封存载荷；保留清理、legal hold 和恢复批准由独立角色执行。共享 NAS、公司共享盘或受保护挂载不得由备份任务自动清空、删除、重挂载或修改 fstab。

## 5. 六个里程碑总览

| 里程碑 | 核心目标 | 完成后能够做到什么 | 未完成时不能宣称什么 |
| --- | --- | --- | --- |
| M1 | 备份范围、恢复合同和基础条件确定 | 知道备什么、如何保持一致、需要多少资源、由谁负责 | 不能宣称已有可恢复备份 |
| M2 | 全量备份与隔离全量恢复跑通 | 在实际规模生成完整备份，并在隔离环境恢复 | 不能只凭备份文件存在判定成功 |
| M3 | 真实增量与全量加增量整链恢复跑通 | 选择任意受支持恢复点，自动解析并恢复完整依赖链 | 不能把单个增量文件当成完整恢复包 |
| M4 | 两个按钮和安全操作流程落地 | 普通操作人能发起备份、选择恢复点、先演练再受控切换 | 不能把页面可点击当成恢复就绪 |
| M5 | 升级、降级、换机和不兼容场景验证 | 只在支持矩阵内恢复；不支持时提前阻断 | 不能承诺任意版本、任意硬件自动兼容 |
| M6 | 实际规模持续运行和最终放行 | 调度、保留、最长链、故障和容量均有实测证据 | 不能把一次成功演练当成长期可用 |

## 6. M1：确定备份范围和恢复基础条件

### 目标

在写实现之前确定数据范围、一致性方式、数据库备份主方案、容量、RTO/RPO、owner 和恢复控制平面，避免做到一半才发现数据无法一致、空间不足或恢复时控制面不可用。

### 必须完成

1. 资产盘点：MySQL 数据库、schema/迁移台账、binlog 或物理日志、MinIO bucket 和对象、DCC/受控文件、Redis、其它业务文件、后端/前端/展厅/OnlyOffice 等程序镜像、配置、部署脚本、证书和密钥引用、外部集成、队列和定时任务。
2. 规模盘点：数据库字节数、对象字节数和数量、每日新增/修改/删除量、增长率、最大单文件、备份仓库和临时恢复空间。
3. writer 盘点：HTTP、Quartz/TenantJob、MQ/worker、外部集成、直接数据库账号和直接对象写入凭据。没有完整 writer 清单就不能建立一致性恢复点。
4. 恢复目标：确定数据库与对象共同恢复点的 RPO、演练 RTO、覆盖 RTO、允许停写窗口、可接受业务性能影响、保留周期和最低可恢复链数量。RTO 的计时起止必须统一，未知值必须标记为 blocker，不能自行假设。
5. 存储与安全：确认离机或独立故障域备份仓库、隔离恢复空间、可用容量、挂载、源/仓库分离凭据、追加/删除权限边界、加密、密钥保管和访问审计。
6. 控制平面：证明业务后端停止时仍可创建恢复任务、查看状态、读取日志和导出证据。
7. 一致性方案：明确 writer 排空、fence、数据库活动事务检查、对象写入拒绝和恢复点 epoch 的形成方式。
8. 数据库主方案实测：在实际数据规模或经批准的等比例数据规模上比较逻辑备份、物理备份或其它候选方案，至少记录停写时间、备份吞吐、临时空间、恢复时间、CPU/磁盘负载和跨机器可迁移性。第一版必须选定一个主方案，不能同时自研多套未验证机制。
9. 数据分类矩阵：区分权威业务数据、可重建数据、派生数据、队列消息、缓存、配置、外部副作用和不可恢复依赖，并为每一类指定备份、重建或隔离策略。
10. 初版支持矩阵：列出 OS、CPU 架构、容器运行时、MySQL、备份工具、MinIO、Redis、程序镜像、schema 和密钥版本的支持组合。
11. 独立恢复材料：确认不可变镜像或可取得的镜像 artifact、恢复工具包、SSH/MySQL/MinIO/TLS/签名/调度/通知等 secret 的独立故障域 escrow、owner、历史 key 版本和隔离恢复验证；秘密不放入备份集明文。
12. 责任与授权：明确备份 owner、恢复指挥人、应用验证人、基础设施 owner、密钥保管人、覆盖恢复批准人和故障升级路径；任何角色缺席时的代理人也必须事先指定。

### 必须产出

- 数据资产与 writer 清单。
- 源环境和目标环境 fingerprint 字段定义。
- RTO/RPO、停写窗口、保留周期和容量模型。
- 数据库全量/增量主方案决策及实测报告。
- 恢复控制平面部署和故障域说明。
- 一致性 epoch、manifest、备份链和恢复候选合同。
- 权威数据、可重建数据、队列/缓存、配置、外部副作用和不可恢复依赖的数据分类矩阵。
- 镜像、恢复工具和 secret/key escrow 的独立故障域与恢复验证报告。
- 恢复角色、批准权限、联系人和故障升级表。
- 初版支持矩阵和 blocker 编码。

### M1 验收门禁

全部清单有 owner、有来源、有更新时间；备份仓库、恢复空间、挂载、密钥引用和隔离目标可被预检查；数据库方案有实际规模证据；恢复控制平面不依赖被恢复的业务后端。

以下任一项缺失，M1 不通过：数据范围不完整、writer 不完整、RTO/RPO 未定义、RTO 起止口径不一致、容量不足、无法形成一致性 epoch、备份仓库与恢复目标未隔离、密钥或历史 key 不可恢复、镜像或恢复工具只能从源机取得、Redis/MQ 策略未定义、法规归档边界未定义或未由数据 owner 确认不适用、数据库主方案未实测。

## 7. M2：全量备份与全量恢复跑通

### 目标

建立第一条完整恢复基线，在实际数据规模上完成一次全量备份，并在空白隔离环境中真正恢复和验证。

### 必须完成

1. 备份数据库、对象、必要业务文件、配置、程序镜像或可取得的不可变镜像 artifact、部署配置、恢复工具版本和密钥引用；仅记录一个可能随时变化的 image tag 不足以支持原服务器不可用后的恢复。
2. 按 M1 定义的 writer fence 和一致性方案固定一个恢复 epoch，记录停写、排空、采集、传输、校验和解除停写时间。
3. 服务器直接向备份仓库传输，支持分块校验、有限并发和明确的资源控制；固定且已校验的传输单元才允许按合同重试。
4. 生成 manifest、文件/对象清单、数据库备份元数据、字节数、数量、全载荷 SHA-256、源 fingerprint 和工具版本。
5. 只有所有必需载荷、manifest 签名和清单校验成功，备份集才从 `VERIFYING` 变为 `COMPLETE`。
6. 在空数据库、独立对象空间、独立 Redis namespace 和匹配运行时中恢复，不能覆盖当前测试环境作为第一次验证；隔离目标必须具有明确的外部副作用阻断证据。
7. 在不触发真实外部副作用的前提下，验证数据库引擎一致性、关键表行数与业务不变量、对象数量和 hash、DCC/受控文件 manifest 与样本 hash、文件下载、文件与数据库关联、登录、关键业务只读路径和后端/前端健康状态；只做抽样登录或只比较文件总数不足以判定恢复成功。
8. 验证隔离槽位的数据库、对象空间、Redis namespace、网络 allowlist、定时任务、worker、MQ consumer、Webhook 和通知均符合 M1 的隔离策略。
9. 验证配置可以从受控配置材料重建，秘密通过独立 escrow 注入；不把明文秘密写入备份集、manifest、日志或恢复报告。

### 几百 GB 的时间要求

业务停写时间不能默认等于全部数据传输时间。只有在源数据仍然被保护、固定状态可继续读取且方案已经实测时，才可以采用“固定一致性副本后恢复写入、后台继续传输”的方式；否则必须安排足够维护窗口，不能承诺只停几秒。

本地快照可以作为采集或回退手段，但不等于独立备份副本。M2 仍必须形成独立保存、可校验、可取得的备份集；至少一份受保护副本必须位于不同故障域，且源服务器运行账号不能删除全部备份世代。

### M2 验收门禁

在实际数据规模完成一次 `FULL`，并在隔离目标完成一次完整恢复。报告必须分别记录停写时长、采集时长、传输时长、校验时长、恢复时长、源和目标容量、数据库关键校验、对象清单和样本文件 hash。

只有“备份文件生成成功”而没有隔离恢复报告，M2 不通过。

## 8. M3：真实增量与全量加增量整链恢复跑通

### 目标

在不重复传输全部数据的前提下，保存数据库和对象的真实变化，并能从任一完整依赖链的恢复点自动恢复出一致的完整业务状态。

### 必须完成

1. 数据库增量使用 M1 选定的真实机制。若采用 binlog，必须记录来源实例、server UUID、GTID 或准确起止位置、连续性和校验，并保证所需日志在增量封存前不会被 purge；若采用物理增量，必须记录基线、父位置和工具合同。
2. 对象增量覆盖新增、内容修改、删除、元数据变化和必要版本信息。删除必须写入 tombstone，不能直接删除历史备份中的旧对象；扫描和传输期间必须引用已固定的对象版本或受保护副本，不能对持续变化的 live key 做两次普通列表差异后就宣称一致。
3. 每个增量点记录 `baseBackupId`、`parentBackupId`、数据库增量区间、对象清单摘要、上一个点的 hash 和 source fingerprint。
4. 恢复候选解析器根据用户选择的目标点自动获取完整链。例如 `F0 -> I1 -> I2 -> I3`，用户选择 `I3` 时，系统自动恢复 `F0 + I1 + I2 + I3`。
5. 缺少、损坏、重复、跨源或不连续的依赖必须精确阻断受影响恢复点；不能因为 `I2` 丢失就错误地禁用仍然完整的 `F0` 和 `I1`。
6. 数据库和对象必须恢复到同一个封存点；第一版不以数据库可按任意时间重放为理由，宣称文件也能任意秒级回退。
7. 恢复之后如果出现新的数据库时间线、源实例重建、对象版本分叉或业务继续写入，必须建立新的 backup generation 和新的全量基线，不能继续拼接旧链。
8. 增量采集失败时，只有数据库日志和对象历史都仍连续、且能从已封存父点无歧义补齐时才允许重试；任一侧出现不可补缺口，必须将受影响候选标记为不可恢复并建立新 FULL，不能静默跳过缺口。

### 必须覆盖的变化测试

| 变化 | 目标恢复点预期 |
| --- | --- |
| 新增文件 | 新点存在，旧点不存在 |
| 同路径文件被替换 | 不同恢复点得到各自内容和 hash |
| 文件被删除 | 删除后的点不出现，删除前的点仍能恢复 |
| 删除后再次使用相同路径上传 | 不能只按路径判断，必须区分旧内容和新内容 |
| 数据库文件关联修改 | 数据库记录、对象内容和恢复后的下载结果一致 |
| 中间增量损坏或缺失 | 依赖该点的恢复候选阻断，原因可定位 |

### M3 验收门禁

在全量基线后连续生成至少三个真实增量点，至少恢复中间点和最新点，并覆盖数据库和对象的新增、修改、删除。故意损坏或移除中间增量、提前清理所需 binlog、在对象扫描期间覆盖同名对象后，系统必须阻断或准确恢复，不能形成假 `COMPLETE`，并保留明确证据。

传输报告必须同时记录扫描量、实际传输量、仓库新增占用、源服务器读写负载和业务停写时长。“增量包很小”不等于“增量扫描成本很小”，也不等于“新机器恢复只需要传增量”。

只有数据库增量，没有对象增删改和整链恢复，M3 不通过。

## 9. M4：两个按钮与安全恢复流程落地

### 目标

把已验证的底层能力接入页面，使普通操作人可以发起任务，但不能绕过一致性、兼容性、恢复链和保护点检查。

### 页面入口

#### 入口一：立即备份

- 页面展示当前源环境、可用空间、上一次成功备份、当前链状态和建议备份类型。
- 请求必须显式传递 `FULL` 或 `INCREMENTAL`；不能因为字段缺失而由后端静默猜测。
- 首次备份、链断裂、恢复后新世代、格式变化或 M6 规定的轮换时，必须明确提示需要全量。
- 如果用户选择增量但前置条件不满足，直接返回阻断原因，不能悄悄改成几百 GB 全量。
- 任务返回 `operationId`，由前端查询服务端任务状态。

#### 入口二：选择备份包恢复

用户先从服务端返回的恢复候选中选择 `selectedBackupId`，查看：

- 恢复点业务时间和封存时间。
- FULL/INCREMENTAL 类型、基线和完整父链。
- manifest、checksum、对象清单和数据库位置。
- 程序镜像、schema、数据库、MinIO、Redis 和目标 host fingerprint。
- `rehearsalStatus`、上一次恢复报告的绑定摘要、演练/覆盖 RTO 估算和容量需求。
- 候选类型、候选失效时间、manifest 签名信任状态和所有 blockers。
- 当前目标与支持矩阵的匹配结果。

然后选择恢复模式：

1. `仅恢复演练`：选择“演练候选”，恢复到隔离槽位，验证结果，不影响当前测试环境；演练完成后才生成绑定当前链和目标环境的演练报告。
2. `恢复测试环境`：只能选择“受控恢复候选（覆盖候选）”，并显式选择 `REPLACE_EXISTING` 或 `REBUILD_EMPTY`。前者要求 pre-restore 保护成功；后者只适用于新机器、空白槽位或已确认不可用的目标，必须证明目标为空、归属正确且不会覆盖其它系统。两者都要求绑定报告仍为 `PASSED`、兼容检查通过、当前权限和二次确认全部通过。

### 后端与安全要求

- 前端或 ChatGPT 网页不能提交任意 host、目录、命令、容器名或数据库连接串。
- 服务端只接受白名单 action 和有时效、绑定目标环境的服务端签发候选 ID。
- 外部备份集必须先通过独立的服务器侧导入任务进入隔离区，再验证 manifest schema/签名、全载荷 SHA-256、大小/文件数限额、路径穿越、符号链接、重复条目、解压膨胀和目标环境声明；全部通过后才能登记为演练候选。浏览器或用户电脑不得中转几百 GB 数据，也不能把任意服务器路径直接变成候选。
- 备份、演练、覆盖恢复和候选查看必须分别受 RBAC 控制；覆盖恢复必须执行重新认证，并由与执行人不同的批准人或已批准变更单完成四眼确认。确认内容必须绑定目标环境、`backupId`、`restorePointId`、`chainDigest` 和影响范围，不能使用可复用的通用确认文本。
- 页面关闭、浏览器断开不能取消正在执行的服务器任务；重复点击必须被幂等键或 operation 锁阻止。显式取消只允许发生在尚未进入不可逆写入阶段，并且必须由后端确认停止、清理临时载荷和释放租约；写入已开始或进程终态未知时只能标记为 `UNKNOWN/FAILED` 并保持目标写保护，不能伪造 `CANCELLED` 或 `SUCCESS`。
- 备份、恢复、发布、数据库迁移、数据清理和环境切换必须共享目标环境互斥租约；无法证明没有并发冲突时不得启动任务。
- 任务状态至少包含阶段、已处理字节、已处理数量、预计剩余、错误码、阻断原因和审计记录。
- operation 状态至少包括 `PENDING`、`PRECHECK`、`RUNNING`、`VERIFYING`、`SUCCESS`、`BLOCKED`、`FAILED`、`CANCELLED` 和 `UNKNOWN`；只有全部恢复后验证通过才能进入 `SUCCESS`，进程中断或终态未知不能自动改成成功。`CANCELLED` 只表示后端确认尚未进入不可逆写入且临时资源已清理；`UNKNOWN` 必须保持目标写保护并等待人工核查。
- 审计记录必须包含操作者、批准人、请求参数摘要、候选摘要、目标 fingerprint、时间、结果和证据引用，并写入业务环境之外的追加式审计存储。
- 页面、日志和证据导出必须脱敏；不得展示或导出明文密码、token、连接串、私钥、完整个人敏感数据或可直接访问备份仓库的临时凭据。
- 当前业务后端停止时，控制平面仍能查看任务状态和日志。
- 隔离演练不得连接真实通知、MQ、Webhook、邮件、短信、外部 API 或其它会产生业务副作用的端点；相关连接必须禁用或指向隔离端点。
- `REPLACE_EXISTING` 前必须形成已验证的保护点。保护点可以是保留的原环境、受保护快照或完整可恢复的最新保护链，不能是未经校验的临时目录。`REBUILD_EMPTY` 不伪造保护点，但必须记录目标为空/已毁的证据、资产归属和批准人。
- 新环境一旦开放写入，自动回退必须停止；必须先保全新旧两边状态，防止回退时丢失新数据。

### M4 验收门禁

通过页面完成一次真实 FULL、一次真实 INCREMENTAL、一次隔离恢复演练和一次受控切换流程验证。至少验证业务后端关闭、浏览器断开、重复点击、版本不匹配、空间不足、链缺失、候选 checksum 失败、演练报告过期和外部副作用端点误配置等阻断场景。

页面能点击但请求没有明确 `BackupKind`、恢复候选由前端任意拼接、演练和覆盖恢复共用一个不可区分的危险动作、缺少重新认证/四眼确认，或不能阻止发布与恢复并发，M4 不通过。

## 10. M5：升级、降级、换机和不兼容恢复验证

### 目标

把“兼容性”从经验判断变成支持矩阵。第一版只支持矩阵内已经验证的组合，矩阵之外必须在执行前阻断。

### 支持矩阵至少覆盖

- OS 和发行版版本。
- CPU 架构、内存、磁盘容量/IOPS/inode、文件系统语义和时钟同步。
- Docker/Compose 或其它容器运行时版本。
- MySQL 版本、字符集、排序规则、`sql_mode`、GTID/binlog 设置和备份工具版本。
- MinIO 版本、bucket、versioning、Object Lock/retention 和元数据语义。
- Redis 版本及其数据定位：缓存、队列还是不可替代业务数据。
- 应用 release tag/镜像 digest、schema fingerprint、迁移台账、配置 schema 和恢复工具 digest。
- 数据路径、挂载、容量、临时目录、网络、证书和密钥版本。
- 外部集成、通知、MQ、定时任务和 worker 是否需要恢复或重新注册。
- 环境专属配置的处理方式：旧 IP、域名、证书、回调地址、许可证、监控 agent 和外部凭据不能从源环境无条件覆盖到新目标，必须通过目标映射和审批后的配置注入。

### 必须验证的场景

| 场景 | 第一版规则 |
| --- | --- |
| 当前程序升级，恢复旧版本数据 | 先恢复匹配旧数据的旧程序；向新程序迁移必须走已验证迁移路径 |
| 当前程序降级，选择新版本数据 | 默认阻断；除非支持矩阵明确验证了逆向迁移或兼容路径 |
| 数据库或备份工具版本变化 | 不在矩阵内就阻断，不能通过关闭版本检查强行执行 |
| 同架构更换服务器 | 只依赖独立备份、镜像、初始化工具和密钥引用完成重建 |
| x86 与 ARM 互换 | 所有应用和依赖镜像均有对应平台且已测试，否则阻断 |
| 磁盘、NAS、路径、IP、域名变化 | 通过目标映射和写入范围预览验证，不得误写生产或错误目录 |
| 证书、回调、许可证或外部端点变化 | 使用目标环境配置重新签发或映射；未经验证不得恢复源环境值 |
| 原服务器完全不可用 | 备份仓库、镜像、工具、配置和密钥恢复路径均可取得 |
| 恢复完成后继续写入 | 建立新的备份世代和基线，不得接着旧链追加 |

### M5 验收门禁

至少完成：一次同架构新机器恢复、一次历史程序版本完整恢复、一次环境专属配置重新映射、一次不兼容组合的提前阻断、一次恢复后新备份世代的全量加增量恢复。新机器恢复必须在不读取原服务器本地缓存、容器层、临时目录或本地密钥文件的条件下完成。

“关闭版本检查后尝试一下”“把旧数据直接灌入新 schema”“把降级当成必然支持”都不能作为 M5 通过证据。

## 11. M6：大数据量持续运行与最终验收

### 目标

证明系统可以在实际几百 GB 数据规模下长期运行，备份仓库不会无边界增长，最长增量链不会让恢复失控，常见故障会明确失败并可定位。

### 必须完成

1. 调度：定时 FULL、定时 INCREMENTAL、任务互斥、超时、积压、失败重试和告警；与发布、迁移、清理和环境切换共享目标环境租约。
2. 保留：按恢复依赖图清理，不能只按文件日期删除；被恢复点、演练/覆盖候选、运行中任务或 legal hold 引用的基线、增量、日志、镜像、工具和数据块不得删除。灾备滚动保留与法规长期归档必须使用不同策略和责任人，灾备清理不能删除仍在法规保存期的记录或对象版本；共享 NAS 或受保护挂载不属于自动清理目标。
3. 容量：同时监控备份仓库、临时空间、恢复目标、数据库重建空间、索引重建空间、快照增长和增长余量。
4. 性能与链上限：记录全量时长、增量扫描量、增量传输量、恢复时长、最大允许链恢复时长、CPU/IO、业务性能影响和停写窗口；根据 RTO 实测确定最大增量段数或最大链年龄，达到阈值前强制建立新 FULL。
5. 故障注入：断网、断电、控制平面重启、业务后端停止、磁盘满、挂载丢失、备份集/manifest 签名损坏、增量日志缺失、密钥不可用、源服务器完全丢失、备份目录索引丢失、源账号被盗、重复点击和任务超时。
6. 持续恢复验证：定期抽取历史点和最新点实际恢复，不能只验证 manifest 或 hash；同时验证历史签名 key、历史镜像、恢复工具和目标映射仍可取得。
7. 最低保护：至少保留两条各自具备完整基线并经过恢复验证的恢复链，其中至少一条受保护副本位于独立故障域，且日常源系统账号不能删除；具体周期由 M1 的 RPO、RTO、威胁模型和容量模型确定。
8. 可观测性：分别监控当前保护点年龄、已证明恢复点年龄、链完整性、日志归档延迟、演练报告年龄、受保护副本复制延迟、容量水位和连续失败次数；任一项超过 M1 阈值必须告警并阻止不安全清理或覆盖恢复。
9. 目录重建：恢复候选目录和 operation 元数据损坏时，能够从独立仓库的签名 manifest、载荷清单和仓库保留元数据重建候选目录；不能要求被毁的业务数据库仍然可用。

### 调度策略的起始候选

以下只是待 M1/M6 实测确认的候选，不是未经验证的承诺：

| 项目 | 起始候选 |
| --- | --- |
| 首次备份 | 建立 FULL 基线 |
| 常规全量 | 可从每周一次开始评估，按变化量、最长链恢复时长和容量调整 |
| 常规增量 | 可从每日一次开始评估；RPO 更严格时提高保护频率 |
| 升级、迁移或破坏性操作前 | 先创建并校验恢复保护点，必要时建立新 FULL |
| 保留周期 | 按业务、RPO/RTO、容量和审查要求确定，不能直接套用固定天数 |
| 新建基线条件 | 链断裂、历史分支变化、格式变化、工具变化、最大链段数/年龄将超阈值或恢复时长超标 |

### M6 验收门禁

至少完成一个完整的调度周期、恢复依赖图清理模拟、法规归档不受灾备清理影响的验证（或由数据 owner 确认不适用）、最大允许链恢复和故障注入测试。必须证明候选目录可由签名 manifest 和仓库保留元数据重建，受保护副本不能被源账号删除。所有 M1 约定的容量、停写、RPO 和 RTO 目标必须有实测结果；未达到的目标必须标记为未通过，不得用“后续优化”掩盖。

## 12. 备份和恢复的标准执行流程

### 备份流程

1. 读取当前环境 fingerprint、链状态、容量、挂载、密钥引用和 writer 状态。
2. 校验 `FULL` 或 `INCREMENTAL` 的前置条件。
3. 获取互斥锁并建立一致性 epoch。
4. 采集数据库和对象状态，写入服务器侧备份仓库。
5. 生成并校验 manifest、checksum、对象清单和数据库位置。
6. 校验完整链和目标存储可读性。
7. 只有全部成功才发布 `COMPLETE` 演练候选；受控恢复候选必须由后续绑定演练报告产生。
8. 记录 operation、耗时、容量、读写负载和可恢复性结果。

### 恢复演练流程

1. 用户选择服务端签发的演练候选，不能上传任意路径或任意命令。
2. 服务端解析完整依赖链并执行 manifest digest/签名、全载荷 SHA-256、版本、容量、密钥、挂载、Redis/MQ policy 和目标隔离检查。
3. 获取恢复锁，在隔离槽位初始化目标。
4. 先恢复 FULL，再按父链顺序应用增量。
5. 恢复数据库、对象和必要配置；保持所有真实外部副作用端点禁用或隔离，再验证关键业务路径和样本文件 hash。
6. 生成绑定 `backupId`、`restorePointId`、`chainDigest`、`manifestDigest`、源/目标 fingerprint、镜像/工具版本、签名信任结果和失效时间的恢复报告，并设置 `rehearsalStatus=PASSED/FAILED`。
7. 演练失败时不影响当前测试环境；失败现场按证据保留策略隔离，到期后受控清理，不能无限保留含敏感数据的临时副本。

### 覆盖当前测试环境流程

1. 只有绑定当前链和当前目标的 `rehearsalStatus=PASSED`、未过期且目标 fingerprint 在支持矩阵内，才能进入预览；执行前必须再次计算 fingerprint，变化即标记 `STALE`。
2. 校验恢复权限、重新认证和四眼确认，并获取与发布/迁移/清理共享的目标环境租约。
3. 显式校验 `targetMode`：`REPLACE_EXISTING` 必须先创建并校验当前环境保护点；`REBUILD_EMPTY` 必须校验空白/已毁目标证明、资产归属和目标写入范围。
4. 停止全部 writer，确认无活动事务和对象写入。
5. 使用目标环境配置和 secret escrow 注入运行参数，禁止把源环境 IP、域名、证书和凭据无条件覆盖到目标。
6. 将数据恢复到新版本化目标或经过验证的快照目标；执行受控切换前保留旧目标只读，整个过程持续记录 operation。
7. 启动新环境并验证后端 health、前端 HTTP、登录、数据库关键数据、文件下载和关键业务只读路径；任一不确定终态都保持写入关闭，不能自动宣称成功或自动回退。
8. 验证通过并重新开放写入后建立新的备份世代；验证失败时保持隔离或进入人工恢复流程。

## 13. 最终放行标准

只有同时满足以下条件，才能对外描述为“测试服务器第一版备份恢复能力完成”：

- M1-M6 全部通过，且没有未解决 blocker；存在任何未通过项时，只能描述为“方案/部分能力完成，整体未放行”。
- 实际数据规模的 FULL 已恢复成功。
- 至少三个真实增量点已生成，中间点和最新点均能整链恢复。
- 数据库和对象的新增、修改、删除均经过验证。
- 备份集有完整且已签名的 manifest、全载荷 SHA-256 和依赖链；对应的演练/恢复证据报告已绑定相同摘要并可独立核验。
- 页面两个主要入口通过后端异步 operation 工作，不能绕过白名单和审计。
- 恢复演练与覆盖当前环境动作分离，未演练包不能覆盖。
- 同架构换机、历史版本恢复和不兼容阻断均有证据。
- 恢复后新备份世代能够再次完成 FULL 加 INCREMENTAL 恢复。
- 调度、保留、容量、最长链和故障注入均有实测报告。
- 关键 owner、共同恢复点 RPO、演练/覆盖 RTO、密钥恢复路径和回退责任人已确认。
- 隔离演练没有触发真实通知、队列消费、Webhook 或外部系统写入。
- 至少一份受保护备份位于独立故障域，原服务器和源账号同时失效时仍能重建候选目录并恢复。
- 灾备保留与法规归档边界验证通过，灾备清理不会删除 legal hold 或未到保存期的数据。

## 14. 第一版明确不承诺的内容

下列能力可以后续规划，但不能用来替代本版必须完成的真实增量、整链恢复和一致性验证：

- 合成全量、跨备份点深度去重等性能优化。
- 任意应用版本之间的自动迁移。
- 任意数据库秒级和任意对象状态的整系统回退。
- 未验证的跨 CPU 架构自动迁移。
- 通过浏览器或用户电脑中转几百 GB 数据。
- 未经授权的生产、正式服或其它环境恢复。

一句话结论：六个里程碑的顺序保留，但 M1 必须把数据库方案、容量、一致性、owner 和独立控制平面定死；M2 必须真实全量恢复；M3 必须真实增量和整链恢复；M4 必须把演练与覆盖恢复分开；M5 必须用支持矩阵阻断不兼容；M6 通过后，才可以对外宣称第一版在实际几百 GB 测试服务器上可持续使用。
