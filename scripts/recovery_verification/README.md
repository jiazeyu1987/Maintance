# Recovery verification v1

The fixed entry is `python verify_recovery.py --request <absolute OperationRequest.json> --output <absolute new OperationResult.json>`. It handles only `VERIFY_RECOVERY`, with the three frozen input keys `restorePlan`, `restoreExecutionResult`, `applicationStartResult`. All paths, Python, target configuration and evidence are selected explicitly by the caller. The verifier performs local evidence reads; it never launches a restore or browser. Output is UTF-8, published atomically without replacing any existing evidence. Exit codes are 0 passed, 1 rejected/blocked/stale, 2 unknown. `actualExitCode` is null because this CLI invokes no child. The raw `RecoveryVerificationReport/v1` is also written to `<output>.report.json` for consumers needing a direct report Pin.

Set `RECOVERY_VERIFICATION_TRUST_PIN` to the JSON Pin of a **caller-selected** `RecoveryCallerBinding/v1`. Never take this environment setting from a producer request, report, output, or automatic hash calculation of whatever happens to exist. Caller independence is established by the service's trust configuration; an arbitrary file's author/complete/success fields do not establish trust. Producer identities must be distinct from the caller. Unknown/missing originals are rejected. The frozen eight business records use the pinned modular `record-schemas.json`; its path is explicit and its bytes/SHA-256 must match the frozen version.

W06-owned records use the exact versions below; they do not change the frozen OperationRequest/business schemas or prescribe W03/W04/W05's internal target-identity byte format. In particular, `sourceOrTargetRef` remains the target configuration original from `RestorePlan.targetRef`; W05's separate `RecoveryTarget/v1` is supplied by `policy.recoveryTargetPin`.

Pins retain their frozen shape. Every consumed original must be in the caller's independentOriginalPins or approved executable scope. The executable scope includes every `.py` in this directory and the running Python executable, plus actual producer/collector tools and their caller-selected dependency/configuration scope. Source lists before and after must match in order and every current byte must match. The report's `sourceScopePin` remains the actual W04/W05 business source; its code audit scope is separately pinned in the caller binding and report evidence. Archive, image, executable and artifact Pins are hashed in 1 MiB chunks under the current deadline, with file identity checks around the read. JSON parsing has an explicit 64 MiB limit; exceeding it fails.

The binding entry is `python bind_caller.py --request <absolute existing request.json> --output <absolute new caller-binding.json>`. The independent caller supplies `RECOVERY_VERIFICATION_SELECTION_PIN`, the Pin of `RecoveryCallerSelection/v1`, with exactly the caller-binding fields above and that selection schemaVersion. W01 must finalize the request bytes/path first. The helper validates the selected request, scope, independent trace/originals and existing invocation authorization, then writes only the binding. It never creates authorization or traces from producer output. `targetApprovalRefs` remain actual invocation grants. W03 must independently select and validate a separate signed post-report approval before controlled promotion.

W04 originals retain their native heterogeneous format: `recovery-invocation/v1`, actual `RecoveryDataRequest/v1`, private stdout/stderr hash summary, `recovery-original-exit/v1`, and `RecoveryDataStepResult/v1`/operation result, plus nested data/import/derived originals. Intent, request, action, operation, plan, target, source, material and recovery point must bind. SQL expansion/import originals retain their actual expanded payload Pins. A terminal verifier may emit both `client-exit.json` and a separate `exit.json` bound through `localExitPin`; remote execution additionally needs independently admitted signed native process/wait proofs and approved authority keys. Unknown termination fails.

W05 app originals are `RecoveryEnvironmentInvocation/v1` and `RecoveryApplicationLaunch/v1`, with real health, preparation isolation, and distinct post-start isolation proofs. Both isolation proofs bind the same target/policy. Post-start proof additionally binds the version-specific write-protection policy, both protection observations, all six business/scheduler/dispatch scopes and actual denied-write invocation originals. A success label alone cannot pass.

Data/browser collection uses `RecoveryInvocation/v1` only as a caller-selected adapter for the actual collection command, bound to this module's collector entry and exact output path. `processProfile` is explicitly `exec-command-result` or `codex-command-event`. The first reads `{id, command, argv, cwd, result:{exit_code, ...}}`; an active session or missing exit is UNKNOWN. The second reads `payload.item` with type=CommandExecution, status=completed, id/command/argv/cwd/exitCode. Both must match the independently pinned invocation. Restore/application producers are never converted into these wrappers.

REHEARSAL retains its existing COMPLETE/rehearsal-eligible admission, including the exact reason `REPOSITORY_CURRENT_RECOVERY_PASSED_REQUIRED`. Every other blocked reason remains rejected. Ancestors must be the exact ordered same-generation chain. `RecoveryVerificationPolicy/v2` is mandatory; v1 is refused. Set `controlledEligibilityPin` to null for REHEARSAL and to an independently selected `RecoveryControlledEligibility/v1` for CONTROLLED_RESTORE.

Controlled admission preserves the original point bytes, including `controlledRestoreEligible=false` and the current-recovery-required reason. It requires an independently pinned prior PASSED report with empty invalidations, matching business source, target, candidate, ordered chain, recovery point, tools and supported versions. All prior report originals must also be admitted by the current caller. The verifier rebuilds the prior report from its original request/binding and actual data, native calls, Playwright artifacts and timing evidence, then applies the current policy's freshness, user paths, protection, data-reference and timing requirements. A PASSED label or eligible boolean cannot replace these checks.

`approvalPin` must select the current W03/W04 `RepositorySignedRecord/v1` envelope (exact `keySha256, payload, signature` after schemaVersion), signed with Ed25519 over canonical UTF-8 JSON by exactly one of the independently pinned `repositoryEvidenceKeyPins`. Its `RepositoryRecoveryApproval/v1` payload has exactly `repositoryId, reportPin, targetIdentityPin, sourceIdentityPin, validUntil` after schemaVersion. Repository, report, source identity and target must match, and both approval and eligibility must be unexpired. The caller's explicitly selected Python must already provide `cryptography` with Ed25519 support; a missing dependency fails verification. The verifier reads existing approvals only. No alternate envelope or v1-policy compatibility path is accepted.

`data` observations and baselines contain exactly `databaseId, tables, objectScopes, objects, references, referenceSpecs, objectTarget, derivedInventoryPin, derived`. Tables contain `name, schemaSha256, rowCount, dataSha256`. The database collector reads every supported base table in one read-only InnoDB snapshot, runs SHOW/DESCRIBE before data SQL, preserves cell types in row hashes, hashes the sorted complete row multiset including duplicates, and rechecks structure/identity. Views/nontransactional tables and unsupported value types fail explicitly; no partial success is emitted. Object scopes contain `bucket, prefix`, cannot overlap, and the collector paginates the complete S3 inventory, reads every object's bytes with IfMatch, hashes content and checks inventory stability. Objects contain `bucket, key, bytes, sha256`; references contain `table, rowSha256, bucket, key, deleted, domain`; reference specifications contain `table, bucket, keyColumn, deletedColumn, domainColumn, allowedDomains`. Every row of each reference table must be accounted for. Deleted-reference handling is an explicit boolean policy. Unknown domains/buckets, wrong bytes, extra/missing rows/objects and uncovered required references fail independently of a successful object restore.

Protection observations contain `scopeSnapshots, sideEffectIsolationPin`; each named snapshot is `{resourceIdentity, sha256}`. Required scope names include `source-environment, tenant-admin, dcc-matrix, showroom-28, bucket-yudao-showroom, external-systems`. Caller-pinned complete before/after fingerprints must match and bracket the original restore/application and browser process. W06 never queries or writes the original protected resources itself; the independently captured fingerprints are required evidence, not generated expected values.

Timing `data` contains `clockDomainId, restoreStartMonotonicNs, userReadyMonotonicNs, recoveryPointUtc, disruptionUtc, clockUncertaintyMilliseconds, restoreStartInvocationPin, userReadyObservationPin, recoveryPointEvidencePin, clockEvidencePin, disruptionEvidencePin`. `RecoveryTimingMarks/v1` contains `clockDomainId, restoreStartInvocationPin, userReadyObservationPin, restoreStartMonotonicNs, userReadyMonotonicNs, restoreStartUtc, userReadyUtc, clockUncertaintyMilliseconds`. Marks must reference the first original restore call and the actual browser observation; UTC boundaries must match their originals. Cross-host monotonic ticks are never combined. A clock discontinuity yields UNKNOWN. `RecoveryPointTimestamp/v1` is `{backupPointPin, recoveryPoint, utc}`; `RecoveryDisruption/v1` is `{operationId, utc}`. All are separately caller-pinned. RTO rounds up; RPO rounds up the disruption-to-common-point interval and adds clock uncertainty. Unknown objectives preserve MEASURED values and yield BLOCKED, never PASSED.

Real collection is a separate, explicitly authorized operation: `python collect_recovery.py --config <absolute config> --output <absolute new observation>`. Set `RECOVERY_VERIFICATION_COLLECTION_TRUST_PIN` to the caller-selected Pin of `RecoveryCollectionCallerBinding/v1` (`callerThreadId, producerThreadIds, configPin, authorizationPin, targetIdentityPin, toolPins, validUntil`). Config is `RecoveryCollectionConfig/v1` (`kind=data|playwright, operationId, restoreId, recoveryPoint, targetIdentityPin, verificationTargetPin, authorizationPin, deadlineMilliseconds, settings`). Tool pins include the complete module and Python/browser executable. The single monotonic deadline is bounded by the authorization window. Credentials are required environment-variable references; driver/browser exception text, passwords and raw rows are not persisted. Failed collection retains a failure record and existing artifacts and returns nonzero.

Data settings contain `mysql, s3, derivedInventoryPin, derivedObservers`; mysql contains `host, port, database, username, passwordEnv, referenceSpecs, connectTimeoutSeconds`; s3 contains `endpointUrl, region, accessKeyEnv, secretKeyEnv, scopes, timeoutSeconds`. PyMySQL and boto3 are explicit dependencies. No remote target, credentials or default database is provided by this module.

Data snapshots additionally contain `objectTarget, derivedInventoryPin, derived`. `objectTarget` is the actual `RecoveryServiceObservation/v1`. `objectBindingPin` selects `RecoveryServiceBinding/v1` with exact fields `schemaVersion, targetIdentityPin, sourceScopePin, environmentConfigPin, resourcesProofPin, dockerPin, machineIdPath, role, endpointUrl, applicationStartPin`. The collector runs on the selected native Linux host, checks its machine ID and explicitly pinned local Docker executable/engine, and inspects the target container/image/network/IP before S3 reads and again afterward. The literal endpoint must equal that target service's actual IP and configured port; a source endpoint or ambiguous proxy is rejected. Preparation binds the container/image/network; the actual application's launch binds its current endpoint. This supports a proven physical MinIO stop/start while preserving target identity. The consumer binds the observation to the same source scope, configuration and exact ApplicationStartResult.

W04's actual `RecoveryDerivedInventory/v1` classifies redis/queue. For each `requiredForBusiness=true` class, `derivedObservers` must contain exactly one independently selected read-only observer with `className, bindingPin, pythonPin, scriptPin, sourcePins, settingsPin, secretEnvRefs`. Its native target service is checked before and after execution. It receives `RecoveryDerivedObservationRequest/v1` on stdin, including actual service identity, fixed recovery point, explicitly selected settings, `writesAllowed=false` and remaining deadline. Its exact output is `RecoveryDerivedState/v1` with `className, operationId, targetIdentityPin, recoveryPoint, complete=true, recordCount, stateSha256, writesPerformed=false`. Python/scripts/dependencies must be in the independently approved executable/tool scope. Secret values are passed only through explicit environment references.

The caller separately pins `RecoveryDerivedBaseline/v1` (`recoveryPoint, inventoryPin, states`); each state has `className, recordCount, stateSha256`. Actual required state must match this baseline for the exact point and actual target. An executor's VERIFIED/exit 0 is insufficient. Missing real read-only observer, service binding, required-class baseline or original evidence fails; this module does not invent a Redis/queue format or observer. When no class is business-required, observer/state lists must be empty and `derivedBaselinePin` must be null.

Playwright settings contain `baseUrl, allowedOrigins, browserExecutable, username=aoteman, passwordEnv, login, paths`. Login contains `tenantSelector, usernameSelector, passwordSelector, submitSelector, tenantIdSelector, tenantNameSelector, identityUsernameSelector`. A **real visible** tenant-id 122/name 测试租户/username aoteman must be proved before business actions and again at every path. Missing real page selectors or entries fail; there is no API/SQL login/data write or mocked response. Each path is `{pathId, entrySelector, steps}` and enters through its actual page/menu selector. Required business path IDs are query, view, download; login is performed first. Steps explicitly use click/fill/text/visible/image/download and selectors, with expected text/value or expectedBytes/expectedSha256 as appropriate. The image check requires rendered dimensions; download checks the actual saved bytes. Paths must contain substantive assertions. The caller must select real existing rows/attachments and read-only business actions; protected DCC/showroom actions are prohibited. Real browser actions additionally require writesAllowed=true for the login/session path, limited to the approved isolated test tenant. The collector blocks external origins, service workers and WebSockets, checks page/business errors, masks the password selector in screenshots and records only assertion/screenshot/download evidence. No browser is run during this development task.

Freshness consumers can import `evidence.assess_report`, or use `python report_currency.py --report <raw report> --current <current binding> --output <new assessment>`. Set `RECOVERY_VERIFICATION_CURRENCY_TRUST_PIN` to `RecoveryCurrencyCallerBinding/v1` (`callerThreadId, producerThreadIds, reportPin, currentBindingPin, schemaPin, maxAgeMilliseconds, validUntil`). The current binding contains operationId/restoreId/mode, the eight report binding fields checked by `report_invalidations`, and reportGeneratedAt taken from the independently pinned original OperationResult.finishedAt. Changes, missing/drifting nested originals, expired observations/authorization/caller binding, or expiry produce a new STALE report with reasons. An old failed/blocked/unknown report is never promoted. Original reports remain immutable.

These capabilities do not confer runtime authorization or certify any NAS/Linux/restored system. Local engineering fixtures check parser/gate behavior only. Full integration, static independent review and real current-target acceptance remain separate stages.

## Local real UI stages

All upload basenames must begin with the actual `runId` followed by `-`; this binds deletion candidates to task-owned files. Source flows must observe the real successful create/update/delete/upload response caused by their UI actions, in addition to checking DOM results. A zero-row deletion check alone cannot certify that a delete occurred. Target deleted checks also require a surviving-row text assertion so an unloaded/failed page cannot satisfy absence. These are passive observations; the script does not issue those API calls itself.

`python run_ui_recovery.py --config <absolute caller-selected stage config> --output <absolute new observation>` runs exactly one `baseline`, `delta`, or `target` stage. `--check --config <absolute config>` checks the real selected inputs, authorization window, dependencies and Pins without opening a browser. There are no supplied URLs, credentials, grants, successful stage fixtures, generated data, or automatic environment selection. Set `RECOVERY_UI_TRUST_PIN` to a separately registered caller-selected Pin; setting it to a producer-selected arbitrary file does not establish independence.

The current local release permits preparation only. Source/target URLs, real account secret references, qualified environment originals and a stage-specific grant must arrive before any login or write. The helper never installs a browser, opens the shared `localhost:8081` app, runs a backup/restore, or uses API/SQL for business actions. All mutation requests outside the explicitly selected source API paths are aborted. Source uploads require the real application's **server upload** configuration; direct browser PUTs to object storage are rejected. This is a prerequisite, not an automatic upload-mode change. Target business writes are rejected; only the actual login session POST is allowed. Origins for source and target must differ, and each stage excludes the other frontend origin. Legacy loopback ports 8081/9000 and DCC/showroom requests are rejected.
