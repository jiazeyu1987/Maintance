# 恢复资源准入与失败收敛

本契约同时适用于安全模式和快速模式。资源准入成功不代表恢复成功或业务验收通过，快速模式原有跳过项仍须记录为 `NOT_PERFORMED`。

## 安装前置条件

- 从本次已提交候选生成并核验两模式包、清单与实际运行文件；不得替换活动操作的执行器。
- 每台目标宿主统一使用 `/var/lib/spug-restore-resources`，由安装过程创建，权限为 `0700`，所有者为实际执行恢复的系统账号。目录必须为真实本地目录，不得使用软链接。不同控制器和两种模式不得使用各自的预约目录。
- 为每个登记目标设置 `resourceBudget`。预算必须依据该来源数据量、展开临时空间、目标资源限额和实际宿主余量制定并留证，不得仅为通过检查调低预算。
- 保留旧操作、目标永久占用及所有失败证据。新增预约目录不解决旧版本缺少启动周期、派发前目标快照等证据的问题。

`resourceBudget` 必须精确包含以下字段，不提供隐式默认值：

| 字段 | 合同 |
| --- | --- |
| `schemaVersion` | `RestoreResourceBudget/v1` |
| `mysqlMemoryBytes` | 正整数，目标 MySQL 所需物理内存上限下限 |
| `hostAvailableMemoryBytes` | 正整数，恢复开始时宿主所需可用物理内存 |
| `diskBytesByPath` | 规范绝对路径到非负新增字节需求的映射，至少一项且总需求大于零 |

磁盘预算路径必须为实际存在的目录，并覆盖操作展开目录、目标数据根和各数据路径；覆盖恢复还必须覆盖 `replacement.stateRoot`。同一设备上的需求合计比较，不能重复使用同一份剩余空间。容器内存同时检查 Docker 配置、实际进程 cgroup 层级和宿主物理内存；swap 不计作物理内存。不会自动扩容、停止其他容器或删除数据腾空间。

## 执行和证据

原 owner 在派发前取得宿主持久独占预约并检查预算；目标永久占用前、覆盖清空前再次验证预约和实际资源。覆盖恢复内部的临时 `dataRoot` 只允许变为原 `replacement.stateRoot/<operationId>/runtime`，其他配置必须与原预约配置完全一致。

- 原操作目录保存不可变 `resource-reservation.json` 和各阶段 `resource-admission-*.json`；原结果包含相应文件 pin。
- 宿主 `active.json` 引用唯一原预约。元数据更新用文件锁串行化；进程结束、SIGKILL、观察超时或重启不自动删除预约。
- 正常成功必须有验证过的 worker 结果及真实子退出 `0`；释放凭据为 `resource-release.json`。
- 已知无变更失败必须明确记录 `mutationDispatched=false`、子退出 `1` 且无超时，并且没有导入器、覆盖准备意图或未完成/有变更的原生调用。释放凭据为 `resource-no-mutation-release.json`。缺字段的旧记录不能推断为未变更。
- OOM 释放只由原查询路径在宿主锁内重新核验完整原结果、进程启动周期/退出、无活动写入者、派发前和当前目标身份及挂载/网络、停止状态、MySQL `OOMKilled=true/137` 和原目标占用。原结果必须已绑定预约 pin；释放凭据为 `resource-oom-release.json`，追加到查询证据。
- 任何上述释放都只移除精确匹配的宿主 `active.json`，不删除目标 `.recovery-operation.json`、原预约、原结果或部分恢复数据。重复查询不改变后来操作的预约。

`RESTORE_HOST_RESOURCE_RESERVED` 表示仍有预约；`RESTORE_HOST_RESOURCE_ROOT_INVALID` 表示安装目录不符合合同；内存/磁盘不足及观测失败各有明确错误码。不得通过清空预约目录、修改旧结果或关闭安全核验解决拒绝。原证据不足时保持阻塞并报告具体缺口。

## 验收边界

本机文件/进程和生成包测试仅证明代码合同。安装完成后仍需核对真实宿主、目标、配置预算与运行代码，再通过真实 Spug 页面分别执行 SAFE/FAST 全量和连续增量恢复，独立核对记录、附件内容、关联关系及新增/修改/删除结果。
