# 通用发布中心

## 2026-10-24 发布前置条件及状态存储

执行器状态使用 `state.sqlite3` 单行 JSON + SQLite WAL 事务，写入采用 FULL 同步。页面仍通过 `/state` 读取，不直接读取数据库文件。持久化失败会阻断页面成功状态和新任务，需调查并重启；不回退旧 JSON、不自动重跑发布。

旧实例必须停掉该实例执行器，运行 `python state_store.py --migrate --root <stateDir>`，再启动新代码。迁移取得同一实例进程锁，逐值核对导入，原 `state.json` 原样保留为历史材料，不再更新。数据库已存在时拒绝重复迁移；损坏时明确失败，不读旧 JSON 代替。备份状态应使用 SQLite backup 接口，不能在 WAL 写入期间只复制主数据库文件。新空实例直接初始化 SQLite。

IntRuoyi 私密配置必须增加 `localBuildSpaceBytes`，分别明确 `worktree`、`package`、`state` 的正整数字节预算。例如本机采用 6 GiB、3 GiB、1 GiB；同一文件系统的预算相加（合计 10 GiB），不按三个独立路径重复消费同一余量。构建前检查完整预算，导出归档前再次检查包及状态预算。缺配置或不足直接失败，不自动清理其他任务产物。预算是本次构建容量下限，不保证其他进程不会同时占用空间；需随项目体积调整。

各远端目标须明确配置 `minimumDockerFreeBytes`（新镜像导入前预算）和 `minimumDockerRuntimeFreeBytes`（镜像已验证导入后的运行余量）。本次三服分别使用 4 GiB 和 1 GiB；数据库恢复点仍单独检查 `minimumStagingFreeBytes`。复用暂存目录必须先核对原包、收据及实际镜像，才能使用运行余量；缺配置直接失败。不得在导入镜像后再次把已消耗的导入预算当作完整剩余空间要求。

三服升级在停止写入之前，由执行器通过 SSH 启动最多 15 秒的验收端口探针，从实际执行器网络请求唯一标识；监听退出后才允许部署。端口被占用或网络不通时阻断。正式隔离环境已有网关，直接检查该网关的验收端口 HTTP 响应；网关 502 仅证明网络可达，绝不代替后续应用健康或登录验收。

验收端口的防火墙权限属于一次性配置，不由每个发布任务自动打开。对使用 firewalld 的目标，显式运行 `python configure_acceptance_access.py --config <private-config> --environment backup --source-ip <executor-fixed-ip> --zone public --apply`，只添加配置端口、指定来源 /32 的运行时及永久规则；脚本核对 SSH 实际来源。无需 reload 整个防火墙。执行器地址变化须重新审查配置并移除旧规则，不自动扩大为任意来源。

该目录提供配置驱动执行器、复用 Spug 原生权限的桥接服务和九页实际操作界面。界面沿用 `output/playwright/spug-release-design/index.html` 的侧栏、标题、流程条、卡片和双栏布局，所有版本、任务、状态来自真实记录。

## 启动与接入

1. 将 `config.example.json` 复制到仓库外私密路径，设置准确源码仓库、子目录、独立 stateDir 和随机 bridgeKey。不要提交私密配置、数据库密码、运行状态或日志。
2. Windows 后台启动 `python executor.py --config <private-config>`。仅启动一个实例；跨进程文件锁防止同一 stateDir 被多个执行器占用。
3. 按 `bridge.config.example.json` 在 Spug 容器可读私密路径创建桥接配置。`origin` 为实际 Spug 来源（如 `http://127.0.0.1:18080`）；`applications` 明确列出应用，已接入项分别配置 `executorUrl` 和与各自执行器相同的 `bridgeKey`；`defaultApplication` 必须指向已登记项。旧版单个 executorUrl 配置不再支持，需显式迁移，不能隐式代用其他应用。
4. Spug 已挂载此仓库 `ops/spug` 到 `/opt/intruoyi-spug`。容器中运行 `python3 /opt/intruoyi-spug/release-center/install_entry.py --bridge-config <private-bridge-config>`。只添加本入口 include，`nginx -t` 后 reload；不重启 Spug。
5. 安装器注册独立 supervisor program，桥接端口18111仅容器 loopback。首次安装曾为当前会话单独启动桥接；本次经用户授权恢复 Docker 后，正常容器启动已自动加载该 program，不再额外启动第二份桥接。容器原 supervisord 没有 supervisorctl 控制段，不改共享控制架构。安装后先核对已有桥接进程和端口，避免重复监听。
6. 正常登录 Spug 后打开 `/release-center/`。桥接使用原生 `AuthenticationMiddleware`，读取 `X-Token`；读需 `schedule.schedule.view`，写需 `schedule.schedule.edit` 且来源匹配。浏览器从既有 Spug localStorage 读取登录令牌，执行器不接收浏览器令牌。

执行器监听端口18110，通过私密桥接密钥授权。数据库端口不映射宿主机；演示前端端口18201～18204只绑定127.0.0.1。应用、数据库、网络、卷统一用配置 applicationId 加环境名；没有应用名称分支。所有写入仅在新建演示资源，禁止将配置指向真实 IntRuoyi 目标。

## 实际发布路径

### 使用本机工具及现有镜像构建

本次演示配置显式设置 `buildMode: "host-local-images"`，并在 `localRuntimeImages` 指定 backend 和 frontend 的已存在镜像。执行器先读取本机镜像 ID，缺失立即失败；不自动下载或切换镜像。当前后端使用 `intruoyi-backend-runtime-base:2026.06.05-jre21-noble-docker29.2.1`（Java 21），前端使用 `nginx:1.27-alpine`。源码 Java 编译目标仍为 17，实际部署运行验证以 Java 21 为准。

Maven、npm 在固定提交的干净 worktree 内编译；生成物被 Git 忽略，编译后再次检查没有源码改动。npm 构建完成后生成 release-info.json，再使用本机镜像 ID 打包。Dockerfile 专用忽略文件允许纳入 target/dist，并排除 node_modules。Manifest 记录构建模式、执行器摘要、Maven/Node 版本及基础镜像 ID。Maven/npm 若缺少依赖缓存仍需联网；失败原样停止。未配置该模式的实例仍按原 Dockerfile 多阶段构建，没有自动降级。

首次选基线 Git 提交构建，在“环境与基线”明确点击初始化三服。仅空白登记状态可执行；未知已有容器和未知数据库结构会失败。初始化创建真实 MySQL8.0.39、执行基线 SQL、启动三套真实应用，不自动通过任何候选包验收。

随后选择候选提交构建。IntRuoyi 顺序：直接测试部署及三项技术检查 → 从当前正式数据库及程序建立独立验证环境 → 原包升级隔离环境及三项技术检查 → 正式原地升级、三项通过后开放 → 同包直接升级备用及三项技术检查。小程序仍使用原演示流程。IntRuoyi 的成功判据以本文末尾“三项技术检查”为准，不再等待人工业务验收。

构建使用专用 detached、固定完整提交且干净的 worktree。版本为北京时间 `yyyy-MM-dd-HH-mm-ss`，Git 提交独立记录。镜像构建后，从前端镜像直接拷出 release-info.json，校验版本后才 docker save。images.tar、迁移文件、release-info.json、manifest 打入 release.tar，包摘要持久保存。发布逐次复核包、manifest、各文件校验和，使用已构建的不可变镜像 ID，不重新构建。

迁移编号格式 `M000001__name.sql`；迁移历史须是已知顺序的连续前缀。未知、running、failed 或校验和差异即阻塞；只跳过 succeeded 且校验和完全匹配项。新包构建前也核对已封包历史 SQL 不被修改或删除。执行 SQL 前 SHOW TABLES / DESCRIBE。失败记录不会自动重试。

每次已有环境升级前暂停应用写入；正式及备用在迁移前保存数据库恢复点，新后端在启动之前放置维护标记，人工验收通过后才删除标记。运行检查覆盖前端200、后端UP、两端版本、目标环境和实际容器镜像 ID。隔离验证绑定实际 SHOW CREATE TABLE 基线结构（排除业务序列计数）、迁移历史、镜像身份及版本，正式和备用升级前重新读取核对。

## 状态与边界

### 分贝通独立应用

应用选择中的“分贝通费用报销助手”进入 `fenbeitong.html`，独立执行器使用 `fenbeitong.config.example.json` 的三服目标及独立状态目录；不会使用 IntRuoyi 的数据库发布器。源码为 `E:/ProjectPackage/fenbeitong/student-collaboration-kit`，目前按本地文件快照构建，页面明确标示源码 SHA256，不伪装成 Git 提交。构建时复制明确列出的源码，在冻结目录构建完整 Node 镜像；`.env`、业务数据、凭据、测试记录不进包。基础镜像必须提前准备，构建不自动切换运行时。

流程：构建完整包 → 测试服部署和人工功能验收 → 正式起点隔离启动演练及确认 → 正式部署和验收 → 同包审查服部署和验收。镜像身份使用 Docker 导出包中的配置摘要，避免 Docker Desktop OCI index 与 Linux Docker 的镜像 ID 差异；每服核对加载镜像和内置版本文件。正式演练复制正式助手自身的数据，禁止外部网络；首次安装演练空数据起点。已有助手取得副本时短暂停止本助手，随后恢复；不停止 IntRuoyi。演练只证明启动路径，不代表全部业务及第三方接口验证。本版没有任意业务迁移脚本执行入口。

各服助手监听 18734，独立数据目录挂载 `/data`，使用该服 IntRuoyi 的票据校验地址。发布前停止旧助手并生成数据恢复点，旧容器保留；部署成功开始运行，业务验收单独记录。未验收、已拒绝、旧包或正式当前包身份不符时不能晋级。发布中断先核对远端原回执，明确成功可只登记结果，明确未产生影响可关闭尝试；部分影响或状态未知交由技术人员处理，不盲目重放、自动回退或丢弃数据。不能把此入口当作已实现所有故障的自动恢复。

Spug 入口与助手业务入口是两件事：IntRuoyi 的助手地址、授权和真实业务配置需要有效，方可完成业务验收。默认不复制本机财务数据、不发起第三方同步或金蝶写入。独立执行器可直接用 `python fenbeitong_executor.py --config <仓库外私密配置>` 运行；本机启用版固定源码摘要，由 `fenbeitong_launch.py` 以当前用户后台运行并在用户登录时启动，日志保存在固定运行目录。应用登记使用独立 bridgeKey 和 executorUrl，保留其他应用登记。

普通发布按已有北京时间 `yyyy-MM-dd-HH-mm-ss` 版本号比较候选包与目标当前版本。测试、正式、备用均拒绝旧包覆盖新版本，也拒绝同版本新建重复部署；不按 Git 哈希、提交时间、按钮点击时间或列表顺序排序。仅构建新包不会使旧候选过期；测试服领先正式服也不阻止已测试候选正常进入正式。备用额外要求所选包就是正式当前已验收并开放的同一个包，部署前核对正式实际版本及镜像。

状态接口返回 `deploymentBlocks[releaseTag][action]`，页面禁用对应按钮并展示原因；执行器在提交和执行前分别检查，远程部署读取实际版本后再次检查。缺失或非法版本不猜测先后，需先核对登记。原 requestId 重复请求只返回原任务，不新建部署；明确恢复及原任务续接沿自身证据校验，不用普通发布按钮降级。重新构建旧源码会产生新的包身份，本规则不替代源码分支审核。

刷新页面不会重复请求；requestId 精确绑定原请求并返回原任务。状态、人工备注、日志、原包身份落盘。服务重启时运行任务标为 interrupted 并阻塞新执行。“任务记录”提供技术核对：保留原状态、任务编号和错误，记录续接或放弃决定。续接前核对实际程序、完整迁移记录和结构；部分迁移、未知状态须先人工恢复，不能点击后自动重跑 SQL。已安装到正式/备用的候选不能通过放弃验收来解除责任。

每个候选包保存独立演练历史，绑定原包摘要、起点指纹、升级执行和业务验收。IntRuoyi 仅允许从正式起点演练；备用直接使用正式已验收绑定的演练证据，核对自身程序镜像、版本、结构和迁移台账与该正式演练起点一致。环境专属运行配置不要求跨服相同，但仍核对目标自身登记基线与迁移前置条件。起点不兼容立即阻止发布，不自动新增演练或改写台账。准备新演练前须明确清除现有隔离环境，历史证据保留。

已有环境可在“环境与基线”选择明确的当前程序包，使用新候选的累计迁移与结构合同只读核对并登记。必须匹配容器归属、程序身份、迁移摘要、列、索引、CHECK、引擎和排序规则；未知结构、未知迁移或失败记录停止，不能补记历史成功。

新包要求 migrations/prechecks.json、schema-contracts.json 为每条编号 SQL 定义预检和执行后的结构。SQL 历史不能修改；预检与合同随每个不可变包封存。预检只能单条只读 SELECT。迁移前对最新数据检查，停写并停止旧后端、确认数据库事务归零后逐步再次检查。镜像先按固定 ID 核对，缺失时仅从原包导入。正式/备用生成独立编号恢复点后再迁移；新应用保持维护，人工验收通过后重载写入门禁并检查健康。

页面独立展示测试、演练、正式、备用的部署结果、业务验收、备注、失败步骤和任务编号。演练历史不覆盖当前起点的验收状态。当前新增路径仍须以真实界面与 MySQL 执行结果为验收依据。

正式验收发现程序问题时，可保持维护，修复后构建新包，重新完成测试、从正式当前实际版本建立的升级演练，再原地发布新包；不能把旧失败包改成通过。新包正式验收并开放后，技术人员可对旧失败验收选择“放弃”，系统重新核对实际新包、结构、迁移和已通过验收，记录替代版本，原失败证据保留。新包尚未验收时不允许解除旧验收责任。

前端版本号编译进 JavaScript，并与镜像内 release-info.json 核对。首页禁用缓存与304重用，避免旧代码读取新版本文件而伪装成新前端。开放业务失败时停止后端并保留维护标记；若关闭动作无法确认，界面明确提示维护状态未知，不记录验收成功。

每个执行器管理一个应用，Spug 桥接按应用目录路由到不同执行器。同一发布中心支持选择多个程序。小程序继续使用本机隔离执行器；IntRuoyi 使用独立远程适配器。没有自动故障回退、自动恢复失败迁移、自动业务验收或无审批数据库覆盖。完整 E2E 结果需由真实浏览器完成后另行记录；编译通过不表示发布成功。

## 应用切换

Spug 首页 `/home` 的原生“便捷导航”已配置“发布中心”卡片：点击卡片下方“小程序”进入 `/release-center/?app=release-inventory&page=0`，点击“IntRuoyi”进入其对应应用页面。原生导航链接在新标签页打开。管理员可用“便捷导航 → 编辑”管理该入口；图标原件为 `ui/release-center.svg`。入口存储在 Spug 自身设置中，无需修改编译产物或增加新菜单脚本。

左侧“当前应用”选择小程序或 IntRuoyi。应用 ID 写入网址 `?app=<id>&page=<n>`，导航和刷新保留当前对象，多个标签页各自以其网址为准。所选包、源码提交、演练起点、技术处理决定和验收草稿按应用隔离；切回时恢复该应用自己的选择。切换本身不创建任务或停止已有任务。旧版未区分应用的浏览器选择不自动归属给新应用。

API 使用 `GET /applications` 读取不含密钥的目录，使用 `/applications/<id>/state`、`/commits` 和 `/actions/<action>` 操作指定应用。写入请求必须带匹配的 `applicationId`。桥接在转发前读取执行器实际应用身份，路由与执行器不符立即停止，防止错误配置把操作发给其他应用。未知应用不自动改选默认对象；默认只用于首次没有明确选择的访问。

已接入应用必须使用不同的执行器端口、applicationId、stateDir 以及目标资源／端口，包和任务由各自执行器保存。当前小程序继续使用原执行器、真实包和任务。IntRuoyi 的独立执行器使用18112端口，读取真实57/58/59目标；只读基线登记不创建数据库，不补记迁移成功。构建入口按精确提交使用新的干净worktree，生成完整镜像并核对镜像内元数据；累计SQL仍须通过历史摘要、策略和目标前置检查。入口接通不等于新版已经发布或业务已验收。

IntRuoyi 首次接入提供显式「补齐当前包版本信息」动作，必须配置真实原包目录、固定manifest摘要、可读取的原始源码提交及各目标原发布目录。动作核对原images.tar及其实际镜像config摘要，逐服确认运行镜像与manifest相符后，只恢复运行容器缺失的release-info.json；已有不一致文件拒绝覆盖。它不改原包、镜像或SQL，也不会签发发布验收；从旧镜像重建仍会缺失。所有新构建继续强制在镜像导出前读回版本文件，不能用这项历史修复替代包验收。

远程执行器的隔离演练要求额外的独立资源及依赖配置；未配置时页面明确禁用。其实现包含正式来源捕获、私有数据库/Redis/MinIO副本和固定原包升级，但尚须真实完整演练与业务验收。历史SQL同ID字节差异和存量业务数据条件不得靠登记基线、修改ledger或重新标记测试通过来绕过。

IntRuoyi 构建使用源码中的 `sql/mysql/release-sources.json`（`release-sql-sources/v2`）明确登记迁移。`migrations` 列出普通迁移文件名；已有 `historicalMigrations` 登记不可变历史原件，`sourceReferences` 登记草案及替代来源；`excludedSources` 记录不参与升级的文件名和原因。顶层 `20*.sql` 必须且只能归属一个分类。目录扫描只发现遗漏，不自动授予发布资格；新增 SQL 即使声明 `allowedEnvironments=test,backup,prod`，未登记也会阻止构建。替代历史修改的后继迁移必须独立登记，不能排除后仍宣称依赖已满足。

日常新增正式迁移时，将文件名加入 `migrations`，并按现有规则补齐元数据、依赖及所需目标检查。只有清单登记改变时无需修改数据库历史记录。首次登记沿用已固定的迁移原件与退役声明，不代表所有存量脚本已经通过真实数据升级验证；最终仍按目标台账生成执行计划，并完成实际隔离演练。旧格式清单不能用于新构建，已有封存包不改写。

### IntRuoyi 发布包 NAS 认证

Windows 远程发布执行器必须配置 `nasPath`（明确 UNC 目录）及 `nasCredentialsFile`（仓库外绝对私密文件路径）。私密文件使用 JSON，包含 `server`、`share`、`username`、`password`，可选 `domain`；目标服务器和共享名必须与 `nasPath` 匹配。构建前和发布包上传前均调用 Windows SMB 认证接口，显式传入该账号，不依赖资源管理器人工登录、不保存系统密码或映射盘符。已存在的不同 SMB 身份冲突会失败，不自动断开其它任务的连接。

认证成功仅证明共享可访问；具体发布目录及写权限仍由真实创建、上传和读回摘要检查确认。包先以 `release.tar.partial` 写入，通过摘要校验后重命名；已有版本目录拒绝覆盖。失败不会改用本地存储或另一个共享。凭据及原始认证诊断不进入发布包、页面或 Git。本机配置变更在执行器下次正常重启后加载，不在运行中的构建强制重启服务。

页面收到旧应用的延迟响应时，核对请求所属的切换代次后丢弃，不覆盖当前应用；发布请求也固定提交时的应用身份。运行 `python -m unittest discover -s ops/spug/release-center -p test_applications.py -v` 可验证目录、拒绝规则及两个真实独立执行器进程的路由身份。


### IntRuoyi：测试直发、正式演练、备用直发

构建固定原包 → 测试服直接升级及三项技术检查 → 正式起点完整隔离副本升级及三项技术检查 → 正式原地升级、技术检查和业务验收后开放 → 同包直接升级备用、检查及验收。

测试部署不要求独立演练。测试验收必须核对实际运行版本、镜像、迁移和结构，不能对已被其他候选替换的版本补签。修改程序或迁移需要新构建、新测试验收和新正式演练；原包始终不可修改。页面仅提供正式演练起点，不再提供测试或备用演练选择。

正式发布必须匹配已通过正式演练的原包摘要、当前起点指纹及升级后结构摘要。正式验收成功后明确绑定其部署消费的演练编号。备用发布使用该编号，核对自身程序镜像、版本、结构、台账与已验证的正式升级前基线兼容，并继续执行备用自身的数据检查、停写后复查和恢复点保护。不同服务器的运行配置或业务数据可以不同；不兼容起点、数据检查失败、缺失正式验收绑定均立即阻断，不能借用其他演练。

仅正式隔离副本要求 rehearsalStagingRoots.prod 和完整 Redis、MinIO、媒体引用、写入进程及外部接口隔离配置。包内 migration-readiness.json 只是静态计划，不能替代真实正式演练与三项技术检查。

SQL 沿用显式 release-sources.json 注册和历史摘要保护；不重写原包、不自动跳过预检、不将业务冲突记为已执行。失败和中断任务继续保留原记录并阻断盲目重试。

### IntRuoyi：三项技术检查（2026-10-23 调整）

每个目标部署后检查：①实际版本和前后端镜像匹配所选不可变包；②迁移台账完整、无待执行迁移且前后端启动正常；③用 Playwright 在真实前端填写登录表单，认证成功并进入登录后的页面。测试和演练按技术检查推进；正式、备用的技术检查与业务验收分别记录，技术检查通过仍保持维护状态，明确业务验收后才开放。演练环境始终独立，不切换为正式环境。

登录后的工作台、工艺路线、审批等业务异常不抹掉已经证明的认证结果，但可记录正式业务验收失败并阻止开放。`mark-tested`、`accept-rehearsal`、`verify-prod`、`verify-backup` 执行技术检查；`accept-prod`、`accept-backup` 必须填写真实验收结论并重新检查后开放。登录工具和凭据必须在仓库外配置，缺失即失败，不使用模拟登录或默认通过。

三项结果及历史分别保存，并绑定目标、原包和任务。正式业务验收失败不能靠重跑技术检查解除；应处理失败原因，或按下面的完整恢复流程回到旧版本。未知迁移及未解决技术失败继续阻断。小程序的既有执行器不在此次调整范围内。

### IntRuoyi：迁移失败和开放业务前的验收失败恢复

正式目标部署成功后保留维护状态，操作人可以记录业务验收失败。迁移中途失败也保留原任务、SQL 台账和错误，不能直接重跑已部分生效的 SQL。在发布页或任务记录中，选择原部署的恢复面板：核对迁移执行状态 → 填写恢复原因 → 恢复升级前版本及数据 → 打开维护验收入口 → 填写验收结果并开放旧版本。刷新不会创建新任务；恢复完成待验收时禁止再次执行数据恢复。

恢复点必须由本版本执行器在停止写入后生成，并绑定原包摘要、原部署任务、旧程序/结构/迁移台账和完整数据。数据库执行完整恢复，包括删除半执行迁移新增的对象；Redis 和 MinIO 恢复登记的数据目录。失败数据库、目录及容器保留为证据。恢复过程中断后沿原恢复日志续接，不重新取得故障后的“起点”；恢复完成仍保持维护状态，只有显式恢复验收才开放。原失败记录保留。测试或正式恢复后，候选包关闭为已放弃，后续修复使用新包；备用恢复不放弃正式已验收的原包，也不回退正式服，可按下述独立补发流程重试备用。

上线前必须在各真实目标配置中明确登记恢复资源，例如已核实两项均使用独占 `/data` 时：

```json
{
  "recoveryInventoryConfirmed": true,
  "recoveryDataMounts": [
    {"role": "redis", "destination": "/data"},
    {"role": "minio", "destination": "/data"}
  ]
}
```

此配置是经过核实的资源范围声明，不能为了通过检查直接照填。需要确认数据库及目录归属、全部写入进程、数据服务能否停机，以及恢复这些目录是否影响其他应用。执行时核对真实挂载、容器身份、空间和文件摘要；配置或证据不完整即停止。隔离环境使用执行器创建的两个独占 `/data` 卷，生成配置同步登记这两个卷，显式冲突配置拒绝运行。旧发布不会自动补造恢复点；已经开放业务的版本拒绝恢复升级前数据，避免丢弃开放后的新业务记录。

### 执行器后台服务与中断核对

Windows 执行器支持专用 SCM 服务 `IntRuoyiReleaseExecutor`。服务描述文件固定源码目录、逐文件摘要、私密配置位置、工具环境和 SSH 身份；不读取随机工作目录中的新代码。首次安装及代码更新需管理员执行 `manage_executor_service.py install/update --descriptor <绝对路径>`。替换旧控制台进程时必须同时提供明确 PID 和脚本路径，并确认没有运行任务或子进程。安装后自动启动、延迟开机启动，异常退出由 SCM 重启；普通启停权限授权给描述文件指定的本机操作用户。

服务私密配置必须显式提供 `pythonExecutable`，指向实际 `python.exe`，用于菜单等构建脚本检查。Windows 服务内的 `sys.executable` 是 `pythonservice.exe`，不能用于执行普通 Python 脚本；缺失或误配时构建失败。三服接入分贝通时，在各目标显式设置 `fenbeitongAssistantHost` 为该服地址；正常部署将此值写入后端 Spring 启动参数并保留其他参数。隔离目标禁止配置真实业务助手地址。

SYSTEM 服务不能直接复用个人所有、个人可读的私钥文件：Windows OpenSSH 可能以权限过宽拒绝加载，即使普通用户连接正常。管理员可运行 `repair_service_ssh.ps1 -Descriptor <当前服务描述文件> -Python <Python绝对路径>`，复制现有身份及known_hosts到独立目录；密钥副本仅SYSTEM和Administrators可读，所有者为SYSTEM，原文件不变。脚本先以临时SYSTEM任务对三服执行只读连接验证，全部通过且服务仍空闲才备份并原子更新配置、重启本地执行器；临时任务随即注销。失败保留真实错误，不放宽私钥权限、不关闭主机指纹校验。后续运行时准备应读取当前服务配置并保留这两个路径，不能重新硬编码个人密钥路径。

停止服务先拒绝新任务，等待当前任务结束。管理命令等待超时不表示任务停止，不强杀发布进程。服务进程异常退出会清理本服务拥有的本机子进程；远端可能继续执行，重启后的任务保留为中断，不能据此认定远端失败。

“中断核对”入口按原任务读取本地进程身份和远端操作回执。仍运行则等待；缺少可确认的终态则保留阻断。构建已停止可核对登记的原包或关闭不完整尝试；修改前失败须确认起点未变。部署已完成但响应丢失时只继续版本、迁移和登录检查，不重跑部署。验收开放响应丢失时核对原验收意图、实际开放状态，再由明确操作完成核对，不代替人工业务验收。

部分迁移使用原任务恢复入口。隔离准备与恢复中断继续使用已有的原副本续接、原恢复日志入口，不另做新副本或重复恢复。旧任务没有统一回执时明确显示证据缺失，不补造过去的执行结果。原失败或中断记录始终保留，并链接后续处理任务；刷新不新建任务。

### 备用服独立补发

正式已验收并开放、备用失败时，在备用页面先处理原失败：修改前失败核对起点后关闭尝试；部分迁移先恢复并验收旧版本；已部署待验收则继续检查或验收，不能重复部署。

满足条件后，“仅补发备用服”固定正式当前已验收的同一个原包，关联原备用失败任务。系统重新核对正式实际版本及镜像、备用实际起点和正式演练绑定，只升级备用。补发使用 `stagingRoot/attempts/JOB-…` 独立目录，保留旧任务的包、恢复点和日志；后续备用验收及恢复继承该目录。旧备用结果归入尝试历史，新尝试重新记录部署、技术检查和业务验收，正式结果保持不变。正式已换包、恢复未验收或备用已安装该版本时拒绝补发。

### 构建与发布前检查

IntRuoyi 的构建、测试发布、正式发布、备用发布页提供独立检查按钮。构建检查绑定完整 Git 提交，验证工具、本地镜像、存储及三服状态；发布检查绑定所选原包，验证摘要、目标起点、迁移计划与对应流程条件，备用补发同时绑定原失败任务。检查采用真实执行器身份，结果持久保存并列出通过、失败和依赖阻断项。刷新不创建新任务；重新检查保留旧结果。

远端检查不暂存镜像、不写数据库、不停启容器，不登记新基线。存储权限通过唯一的临时本地/NAS文件完成写、读、改名、删除验证，不触碰已有文件。诊断失败不成为部署失败锁；诊断中断必须重新检查，不标记成功。诊断运行期间不允许并发发布。

通过只代表所列条件在该时刻通过，不代表程序功能或迁移业务数据已经验证。实际发布仍执行已有的包、数据预检、起点、维护和恢复点检查；不会因曾经检查通过而跳过演练、验收或停写后的复查。检查不自动清理空间、修复业务数据、构建或发布。

## 发布产物清理

IntRuoyi 发布中心 → 产物清理（`page=9`）：选择保留最近版本数（默认3、至少2），扫描后展开明细，勾选可清理的位置/版本，输入“确认清理”再执行。扫描不删除产物；第一版不安排自动清理。

额外保留真实三服和验证环境当前版本、正式上一稳定版本、基线、未完成发布及未解决故障所依赖的版本。任何容器（包括停止容器）引用的镜像都保留。未知归属、缺清单或摘要不一致的目录明确列为保留；旧恢复记录缺少版本/任务绑定时保留该版本，不自动补造归属。

清理仅针对登记目录中的发布包/镜像归档、明确归属的过期恢复 SQL 和卷归档，以及清单登记的闲置镜像标签。不清理数据库、数据卷、构建缓存、未登记目录或失败现场；manifest、迁移脚本、恢复记录与任务审计继续保留。镜像按标签删除，不强制删除、不执行 Docker prune；共享镜像层可能不释放空间，页面仅汇总已核实文件大小，未统计目录明确标注。

预览绑定扫描任务，30分钟内单次使用。清理前重新扫描版本、保护条件和文件身份；发生变化就停止。逐项记录已删除项及失败项，部分失败不记整体成功，必须重新扫描再处理。被清理的包标记为产物已退役，后续禁止重新发布，原版本及审计记录不抹除。
